# Security

FreeDuet agents read your mail, browse the web and can, with your approval, spend money. Security is a feature, not an afterthought. It is safe by default; if you want, you can turn on Full access for a member, which removes most of its approval cards, with or without payments; what still asks is under [What asks you, and what does not](#what-asks-you-and-what-does-not) and in [docs/FULL_ACCESS.md](docs/FULL_ACCESS.md).

## Reporting a vulnerability

Please **do not** open a public issue. Use GitHub's private vulnerability reporting on this repository ("Security" tab → "Report a vulnerability", or directly [github.com/MarcoDeliaBot/freeduet/security/advisories/new](https://github.com/MarcoDeliaBot/freeduet/security/advisories/new)). We acknowledge within 72 hours and aim to fix critical issues within 14 days. Do not include real credentials, personal data or conversation contents in a report.

Especially valuable reports:

- any way an agent completes a purchase, booking, send, signature, publication or deletion **without** an approval event, other than the cases listed under [What asks you, and what does not](#what-asks-you-and-what-does-not) (Full access, a saved "Always allow", a typed recipient, a standing mail rule), or by words the fixed rule misses, which is a known limit and still worth a report;
- any way Full access gets turned on, or changed, by anything other than the person in their own signed-in session: a member, a routine, a hand-off, a skill, a connector, or text in a mail or a page;
- any way Full access reaches a routine, a check-in, another member or another person, or lifts the refusal of a password, credential or security setting;
- any way a member set to Full access without payments completes a payment, a purchase or a transfer of money without an approval event, a hand-off from another member included;
- any way a member types into a password, one-time code or card field on its computer (D76), or a write on the Routines connector goes through with no card;
- any way FreeDuet code reads or transmits a provider's subscription credentials;
- any way content an agent reads (an email, a web page, a document, an image) makes it act;
- any way a CLI engine reaches the host outside the tool bridge;
- any way a member's computer reaches a device on the home or office network, or a cloud metadata address, while "Home and office network access" is off (a name that resolves there, a redirect, a script on a page, an unusual way of writing an address);
- any way a purchase permit is reused, extended or applied to another merchant or total, once permits exist (planned for v0.4, not built).

## Threat model

| Asset | Threat | Control |
|---|---|---|
| Money | An agent buys or books what you did not approve | Today: a payment found by the fixed rule's words is handed to you, with no "Always allow", unless that member is on plain Full access; one the words miss is left to the reviewer model (see below). Planned for v0.4, none of it built: single-use purchase permits bound to merchant host and total, valid 10 minutes; caps per purchase, day and month; a gateway rule on checkout clicks; the final summary re-checked before the last click; a minimum engine tier for buying |
| Subscription accounts | Credentials stolen or misused; account suspended | FreeDuet never handles subscription credentials; only official, unmodified CLIs; routes off when provider terms are unclear ([docs/PROVIDERS.md](docs/PROVIDERS.md)) |
| Site logins and payment details | Leaked into chat, logs or the model | Masked secret box and take-over; credentials encrypted, write-only, redacted from audit. A member's computer refuses to type into a password, one-time code or card field, below the approval gate and in every approval setting (D76); the markers it reads and what it does not catch are under "What asks you, and what does not" |
| Your data | Exfiltrated by prompt injection | Read content is data, never instructions; tool arguments that carry credentials are refused before the call leaves; a send is judged against what you typed and asks unless it is clearly what you asked, with the exceptions listed below; telemetry off by default |
| Your machine | An agent escapes to the host | One computer per member where the container supervisor runs (`scripts/start.sh` starts it unless `OPENBOT_ONE_COMPUTER_EACH=false`), each a container with capabilities dropped, and one shared computer otherwise; CLI engines with no built-in tools; the computers' and the supervisor's ports published on loopback only; each member's computer opens for a token of its own, made by the supervisor from its own secret and the member's id and held by no other computer, so the token a prompt-injected shell can read from its own container (it can: the shell's parent process is readable) opens that computer and no other. The one shared computer, and a Kubernetes Sandbox, still take the deployment's one `COMPUTER_TOKEN`, so they have no such separation ([docs/design/per-computer-token.md](docs/design/per-computer-token.md), not yet run on Docker); a connection that comes from this machine's loopback is answered only under this machine's own names, which a connection through a published Docker port is not ([docs/M1_PLAN.md](docs/M1_PLAN.md), section 23) |
| Your home or office network | A page, a mail or a prompt injection sends an agent's browser or command to your router, a NAS, a printer, another computer or the cloud metadata address | Refused by default in the computer's own network filter, on the address the connection really goes to: the filter resolves a name itself and checks every answer, and a redirect is a new connection. Private, loopback, link-local and shared-address ranges, in every way of writing an address. One switch, "Home and office network access", lets the private ranges through; cloud metadata stays refused either way. Not covered: a command that opens a raw socket and ignores the proxy settings, which on Docker Compose needs a network-level control ([docs/M1_PLAN.md](docs/M1_PLAN.md) D36) |
| Your reputation | Something is sent or published in your name | A send or publish that asks shows the exact text and recipient before it goes; the cases that go without a card are listed below, and Full access is one of them |
| Your approvals | A member, a mail or a page switches Full access on, or it spreads beyond the member you chose | Off by default. Only your own signed-in session can write the setting (no member tool, no route a member can reach); it applies to one member, in your own live chat only (never routines or check-ins). It does not call the reviewer for an ordinary action: whatever the fixed rule's words do not find goes with no card, so in both settings a payment the words miss goes, and with plain Full access a payment the words find goes too, while a credential or security change the words find still goes to you. A command or a script write is read once by the reviewer under Full access (D77), and a routine's write, a routine or trigger setup, a setting changed from chat, the programs on your computer and a remote session still ask with a card every time. Plain Full access has no limit on an amount until spending caps exist (v0.4). Each action taken without a card is on the audit trail, with the setting that allowed it |

## What asks you, and what does not

The rules as the code on `main` reads them today. References are in [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md), T1, T3 and T5.

- **The fixed rule.** A payment, a password or credential and a security setting go to you when words from a list appear in the tool's name, its scope, its arguments or its target (`safetyRequirement`, `SAFETY_REQUIREMENTS`). The lists are English and Italian only. A button named "Pay now" is caught; "Buy" or "Place my order" is not.
- **What the words miss** is judged by the reviewer model. Review is on by default and "ask before every change" is off by default. If you switch both off, a change the words miss runs with no card.
- **A send, signature, booking, publication or deletion** is judged by the reviewer against what you typed, and asks unless it is clearly what you asked. These go without a card: a new email whose every recipient you typed in your own latest message of your own live chat (D27, D27a); a standing mail rule you set in your own words (D46), which then runs by itself and can only label, archive, mark as read or move mail to Spam or the Bin; a mailbox change on a tool you saved "Always allow" for; and what a member on Full access does, within the limits of the next three bullets.
- **Full access** is off by default, set per member, and applies only in your own live chat. In both settings it acts without a card on whatever the fixed rule's words do not find, and it does not call the reviewer for an ordinary action, so what the words miss goes with no card, a payment included. A password, credential or security setting that the words do find still goes to you. The two settings differ on one thing: plain Full access also acts without a card when the words find a payment, with no limit on the amount; "Full access without payments" still hands you a payment that the words find (`fullAccessOutcome`).
- **What Full access does not lift.** A routine's or a trigger's write, setting up, changing or deleting a routine or a trigger, a change to one of your settings made from chat, anything done to the programs on your computer (reading the list too) and every write made in a remote session ask with a card every time, with Full access on or off (D35, D60, `alwaysAskReason`). Starting a standing mail rule is not lifted either: it goes without a card only when your own typed words ask for that rule. A rule an administrator made for the team, which asks or hands the action to you, still applies.
- **Commands and scripts in a member's own computer.** The fixed rule's words are not applied to `computer_run_command`, `computer_write_file` and the like (`NOT_ACCOUNT_ACTIONS`). Since D77, while review is on, the reviewer's safety category is applied to a command and to the write of a script (a script extension, or contents that start with `#!`): a payment, a credential or a security change that it names is handed to you. Under Full access the reviewer reads each command and each script write once, even when you switched the reviewer off, but only when a reviewer model is set up: a credential or security change is handed to you in both settings, a payment in "Full access without payments", and a command or script too long to read in full (6000 characters) is handed to you. It only ever adds a hand-off. Limits: a file with no script extension and no `#!` line that is written and then run is not read, only the command that runs it; a payment or password change hidden in a heredoc, `curl | sh`, base64 or `$(...)` is found only if the model reads it; with no reviewer model set up (a fresh install) or a reviewer that fails, nothing is added; each command and each script write costs one model call. A routine's command or file write gets no always-ask card: the normal gate and the reviewer decide it.
- **Typing.** A member never types a password, a one-time code or a card number: the computer itself refuses to, whatever the field is labelled and in every approval setting, Full access included, and the member asks you to type it yourself, in the live browser view or on the site (D76). The refusal is made on the member's computer, below the approval gate, so a saved rule, the automatic reviewer and Full access cannot lift it. It reads the page's own markers: a password field, an `autocomplete` token for a password, a one-time code or a card, text drawn as dots, or a field a secret was entered into before. Not caught: a field with none of those markers (a password box that a "show password" button turned into plain text), a virtual on-screen keypad that is entered by clicking, a closed shadow root on an ordinary tag, and a member's shell that drives the headed browser's display.
- **Purchases.** There is no purchase permit, no cap per purchase, day or month, and no checkout gate yet (planned for v0.4). A spend ledger exists only for metered engines, and none can run in this release.

## Safe defaults

- No spending cap is built yet: caps per purchase, day and month are planned for v0.4. Until then, payments and purchases ask you, unless you turn on plain Full access for a member, which has no limit on the amount.
- Metered APIs: off in every chain until you enable them. A paid engine gateway is refused until FreeDuet can enforce your spending limits; the caps in `engines.yaml` are read but not yet enforced.
- Full access: off for every member until you turn it on, one member at a time, after a warning, in one of two settings (with or without payments). What it lifts and what it does not is under "What asks you, and what does not".
- Home and office network: a member's computer cannot reach it until you switch on "Home and office network access" (Admin > Enterprise controls > Capabilities).
- Telemetry: off.
- Where conversations are kept: `scripts/start.sh` writes `FREEDUET_INTELLIGENCE` into `.env` when the line is missing: `off`, which keeps them in your own database and sends nothing to CopilotKit, unless all three Intelligence settings are already there, then `on`. `.env.example` says `off`. The server has no default of its own: it refuses to start when that line is missing (D65). The desktop app writes `off` when its settings hold no value (D67, 17 November 2026; a value the person wrote, `on` included, is kept), and the Helm chart writes `on`, which keeps conversations in CopilotKit Intelligence; the chart's default is not decided yet.
- Secrets: none ships with the repository. The first `bash scripts/start.sh` makes a value of its own for each secret FreeDuet needs (the tokens of the computers and the supervisor, the routines worker's secret, the database's password, the key that seals saved logins), writes them to your `.env`, readable by you alone, and shows none of them. No two installations share one. An installation that started before this is moved off the old shared values on its next start and keeps its data; `start.sh` says what it could not change, and why. One that already holds saved logins or connections keeps the example key until you run `bun scripts/rekey-vault.ts --apply --yes` from the `openbot` folder, which seals them again with a key of its own, on purpose, after a backup ([docs/design/vault-rekey.md](docs/design/vault-rekey.md)). Details in `docs/M1_PLAN.md` (D39).
- The app listens on localhost by default: the install scripts do not set `OPENBOT_HOST`. The container image sets it to `0.0.0.0` inside the container, so there only what `-p` publishes decides who can reach it: publish on `127.0.0.1` (`openbot/docs/deployment.md`). With `OPENBOT_SINGLE_USER=true` and `OPENBOT_HOST` set to an address that is not loopback, everyone who can reach the port is the administrator, with no sign-in and no installation secret; the boot log says so. Put TLS and sign-in in front of it before exposing it to a network.
- A person's first sign-in makes their conversations with the team, and nothing else (`person-team.ts`). Iris's daily review is offered, not made (D79): Iris offers it once, as one line of her first proposal, and it is a routine only after you say yes and allow the card that every routine setup gets. It can be changed or stopped on the Routines page.
- Iris holds the Routines connector by default, granted once at the first start and only to her (D81, `iris-routines.ts`); a grant an administrator removes stays removed. Every write on that connector (create, change or delete a routine or a trigger, pause or resume a trigger) asks with a card every time, with Full access on or off, and a call that carries an argument the tool does not declare is refused before any card exists. The two reads, listing routines and listing triggers, ask nothing: Iris's model sees your routine instructions and trigger addresses in her turns.
- Background research, where a member reads your connected mail and calendar every few hours, is off until you switch it on (D78). At the update that made it so, every existing research setting was switched off once, keeping its focus and interval, and a later change to a setting never switches it back on (D80). A deployment whose administrator sets `OPENBOT_PROACTIVE_DEFAULTS=true` switches it on by default for people who have no setting yet.
- With no sign-in, a request from this machine is answered only when it names one of this machine's own hosts (`localhost`, `127.0.0.1`, `[::1]`) or a host you configured in `TRUSTED_ORIGINS`; any other `Host` gets 421. This keeps a web page that re-points its own name at 127.0.0.1 from reading your local FreeDuet. Details in `openbot/docs/configuration.md`.

## Independent checks

- CodeQL (GitHub code scanning, JavaScript/TypeScript and Python) runs on every pull request and once a week; zizmor checks the workflow files themselves whenever one changes and once a week.
- The OpenSSF Scorecard, which scores how the repository is run, runs on every push to `main` and once a week.
- Releases from now on carry a signed build-provenance attestation for their source archive ([.github/workflows/release-provenance.yml](.github/workflows/release-provenance.yml)); how to check it, and every other claim here, is in [docs/VERIFY.md](docs/VERIFY.md). What was considered and what was not is in [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md).
