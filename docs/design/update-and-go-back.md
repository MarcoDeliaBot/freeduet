# Updates that can go back: the command

First slice, merged as PR #245: the command `openbot/scripts/update.sh`, its tests, and a page about it in the configuration docs. The roadmap row "Updates that can go back" says: "Run live on one installation on 15 November 2026: the update was run four times, each time with a database backup taken first. The step that puts the version and the data back is not among those runs." What was tested, and how, is in section 4. Written 2026-11-15 against origin/main as it stood that day, and revised the same day after an independent review of the pull request (eight fixes, listed in section 4).

The product decision is the roadmap row "Updates that can go back" [code: docs/ROADMAP.md]: one command updates FreeDuet, copies the data first, checks that the app answers, and if it does not, puts back the version and the data the person had, by itself. The copy stays on the person's computer, readable only by them. Nothing is updated without the person's command. The notice in the app that a newer version exists is the next slice and is not built here.

Markers: [code: path:line] is a line of this repository at that tree. [assumed] is not checked here. Paths are from the repository root.

## 1. What the person sees

In the folder they cloned FreeDuet into, with FreeDuet running:

```
bash openbot/scripts/update.sh --check        look, change nothing
bash openbot/scripts/update.sh                update to the newest release (the newest v* tag)
bash openbot/scripts/update.sh --to <ref>     a tag, a branch or a commit
bash openbot/scripts/update.sh --main         origin/main, the development version
```

It starts with a look: where they are, where it would go, which Docker project it works on, where the copy will be, and the five steps in order, then one line that says to pause anything that restarts FreeDuet by itself. It asks nothing. `--check` stops there ("This was only a look. Nothing was changed."). Without it, it runs the steps and says each one in plain words:

1. Stopping FreeDuet, then waiting to see that nothing starts it again (up to 75 seconds, `--watch`).
2. Making a copy of the data, with nothing else running.
3. Moving to the new version and installing what it needs.
4. Starting it. This is `scripts/start.sh`, which brings the database up to date.
5. Checking that the app and the API answer (about 120 seconds, `--wait`).

It ends in one of four ways:

| Exit | What the person reads | What is true |
|---|---|---|
| 0 | "Updated. FreeDuet is now on v0.3 and answers at http://localhost:3010." Or "Already up to date." | The new version runs and answers. Older copies beyond `--keep` were removed. Also when Ctrl-C comes while they are being removed: "The update is done", the result stays `updated`, and nothing is printed to go back with |
| 10 | "The update did not go through. You are back where you were: v0.2, with your database and your settings as they were." and where the copy is | Code, `.env` and database are what the copy held. The old version runs and answers |
| 20 | `Going back did not work:` and the reason, then the exact commands, in the order to run them | The person finishes by hand. The copy is never deleted. Also used when something started FreeDuet again while it was stopped, and for Ctrl-C after the stop (if that came while the database was being put back, it says the database may be half restored and to run the commands again from the first) |
| 1 | The reason, and "Nothing was changed." | It refused before it changed anything |

The copy is a folder, `~/.freeduet/updates/update-<YYYYMMDD-HHMMSS>` (`--copies` puts it elsewhere): `database.dump` (what `pg_restore` reads), `env.copy`, `role-password.sql`, and `record.txt` (what they were on, where it went, how the run ended: no secrets). The folder is 700 and each file 600. It holds every secret that `.env` and the database hold, and the command says so each time it names the folder.

## 2. Rules

The order is the safety. Everything from the stop on ends at the copy.

- **Looks first.** It refuses, says why, and says "Nothing was changed." when: a tracked file has changes of its own (modified or staged: an update would not keep them), a merge or rebase is half done, the database does not answer (FreeDuet has to be running to be updated), the settings point at another database than the one Docker starts here (user and database `openbot` [code: openbot/docker-compose.yml:18]), the folder is not a git checkout (the installer allows a ZIP [code: openbot/scripts/install.sh:7]), the target cannot be reached by moving forward (older, diverged, unknown), a file of the person's own is where the new version brings one, there is no room for the copy, the disk does not keep file permissions, the folder for the copies is inside the repository, another update is running, a tool is missing (including `sha256sum` or `shasum`), or the postgres container that Docker finds is not this installation's (next bullet).
- **Whose postgres.** `docker compose` finds a stack by its project name, and with no `COMPOSE_PROJECT_NAME` the project is named after the folder, so two checkouts that both sit in a folder called `openbot` share their containers, and `compose exec postgres` (or `stop.sh`) run in one could act on the other's database. Before anything is stopped, the postgres container that `compose ps --quiet postgres` finds must be exactly one, and its `docker inspect` labels must name this checkout (`com.docker.compose.project.working_dir`, or the folder of the first of `com.docker.compose.project.config_files`, compared by name and then by where it really is) and the project that `COMPOSE_PROJECT_NAME` names (in the settings file or in the shell; if both are set and differ it refuses, because Docker would use the shell's). If any of that fails, or Docker will not say, it refuses with "Nothing was changed." The project goes in the plan and in `record.txt` (`compose_project=`). The second stack on the maintainer's machine (`OPENBOT_ENV_FILE=.env.eval`, project `freeduet-eval`, ports 3110, 3101 and 5442 [code: openbot/scripts/freeduet-eval-stack.sh:77-95]) is the same checkout, so the folder cannot tell it from the first stack: the project does. A run for either reads its own settings file, its own ports and its own project, and a test builds a machine with both stacks and shows that a run for one leaves the other's database, password, containers and ports exactly as they were.
- **The copy is made after the stop, with only the database running.** A copy taken from a running FreeDuet misses what happens between the copy and the stop, and going back would lose it. With the app, the API and the worker stopped and nothing else connected, asked twice a second apart through `pg_stat_activity` (as the adopt tool does [code: openbot/server/src/freeduet/adopt/preconditions.ts:185]), nothing can be missing.
- **Nothing changes until the copy exists and has been checked.** `pg_dump -Fc -C` runs inside the postgres container. The file must be at least 512 bytes, begin with `PGDMP` [code: openbot/server/src/freeduet/adopt/backup.ts:322] and be readable by `pg_restore --list`. Its sha256 is taken and written to `record.txt` (`database_sha256=`). `.env` is copied and compared byte for byte. The folder is 700 and the files 600, checked after they are written [code: openbot/server/src/freeduet/adopt/backup.ts:277] [code: openbot/server/src/freeduet/adopt/backup.ts:289]. If a check fails it goes back at once, with nothing changed.
- **Fast-forward only.** `git merge --ff-only`. The person's own commits, or a version that is not ahead, are refused and never merged. For `--to <name>`: when a local branch `<name>` and `origin/<name>` both exist and the local one is behind, it takes `origin/<name>` (the local branch is whatever it was when it was last updated; `origin/<name>` was just fetched), and it says which ref it took; a local branch with commits that origin does not have is the person's own and is used as it is.
- **Going back, in this order.** Stop what the new version started (`scripts/stop.sh`), reset the code to the recorded commit, put `.env` back, run `bun install --frozen-lockfile` if the code had moved, check the copy again, restore the database and the database user's password, start the old version with `scripts/start.sh`, check that it answers. The database is restored only if the new version had been started, because starting it is what migrates the database [code: openbot/scripts/start.sh:646]; before that the command says "database: not touched, so it is as it was". After a restore it compares the database with what was copied (number of tables and of migrations). If they differ it exits 20.
- **The copy is checked again right before it is used.** A restore starts by dropping the database, so a copy that is not the one that was checked when it was made must never reach it. After the quiet check and before the restore, the sha256 of `database.dump` must equal the one recorded and `pg_restore --list` must read it; a file that is missing fails the same way. If it fails, the database is not touched and the command gives up with exit 20. It then does not print a command that restores from that file (a restore from a damaged copy drops the database and stops, which is the loss this check exists to prevent): it prints how to check the copy by hand (the checksum line and `pg_restore --list`), says to restore from another copy of the file if the person has one, and prints how to run the new version again on the database as it is (merge to the target, `bun install`, `start.sh`). The by-hand list printed on every other failure also has the checksum line before the restore, and the person is to run the restore only if it says OK. At that point the new version is stopped, the code and `.env` are back on the old version, and the database is as the new version left it.
- **The restore is whole, or it says it is not.** The dump is made with `-C` and restored with `pg_restore --exit-on-error --clean --create --if-exists --no-owner -U openbot -d postgres`: the database is dropped and made again from the copy. This was checked on a PostgreSQL 16 test cluster, not on the pg17 image that Docker starts [code: openbot/docker-compose.yml:3], and the two are [assumed] to behave the same here: with plain `--clean --if-exists` over a database that a newer migration had added a table with a foreign key to, the restore stopped on that table and left a mix of the old and the new. It will not restore while anything else is connected.
- **The database user's password.** `start.sh` may set a new password on the `openbot` role [code: openbot/scripts/start.sh:612]. A role's password lives in the cluster, not in a dump, so restoring the database and `.env` would leave `.env` naming a password the role no longer has. The copy keeps the stored hash of the password (not the password) in `role-password.sql`, mode 600, and going back sends it to `psql` on standard input.
- **A watchdog.** Something on the computer may start FreeDuet again when it stops. One does exist: it restarts the stack within a minute of port 3010 going quiet, and two starts collide once before one wins [code: CLAUDE.md, last section]. The command looks for that for up to `--watch` seconds after the stop (75: that minute and 15 seconds more) and ends the wait the moment it sees the stack back. It asks again before the copy, before the move and before a restore. If the stack is back it exits 20 and does not touch the database or the code, and it never starts FreeDuet on top of whatever did. Pausing the watchdog first is the advice in the docs [code: openbot/docs/configuration.md, section "Moving from no sign-in to sign-in", step 3]. A watchdog that restarts the stack while `bun install` or the new `start.sh` run would collide with them, and the commands the person runs by hand to go back stop and start FreeDuet too; so the plan the command shows before it stops anything says "pause anything that restarts FreeDuet by itself", and so does the list of commands it prints. There is no prompt: the person's own command is the approval.
- **Ctrl-C and stops.** Before anything was changed it stops, exit 1. After the stop it exits 20 and prints what to run; if the stop came while the database was being put back it also says, plainly, that the database may be half restored, not to start FreeDuet on it, and to run the printed commands again from the first one. Once the update has worked (the app and the API answered) the success is said first and old copies are tidied after; a Ctrl-C or an unexpected stop in the tidying says "The update is done", exits 0 (a script that dies of a signal it does not handle reports that signal, whatever its exit trap says), leaves the result `updated` and prints nothing to go back with: going back there would roll the database back from an update that worked.
- **One at a time.** A lock folder, `openbot/.logs/update.lock`, holds the process number of the run. A run that finds the folder without a number waits up to 5 seconds for it, because the owner may have made the folder a moment ago and not yet written who it is; only then is it taken as left behind.
- **Where the copies go.** Never inside the repository (links resolved, also when the folder is not made yet; `..` in a part that does not exist yet is refused): a copy holds every secret, and a `git add`, `git clean` or `git stash` there could publish or delete it. The default is `~/.freeduet/updates`.
- **Secrets.** Never printed, logged, or on a command line. They are in the 600 files and on standard input only. A test plants canary values in `.env` and in the database user's stored password, and fails if any of them shows up in anything the command printed, ran or logged outside the private copy, or on a command line. The script holds no path of any CLI's login or settings folder and none of the published example values (both tested).
- **Logins first.** The command calls no model and no metered API. It talks to the git remote (`git fetch --tags origin`, the one thing `--check` asks the network) and runs what `start.sh` already runs.
- **Approvals.** No approval is touched. The person's own command is the approval, and nothing runs it for them.
- **What it deletes.** Only old copies it made for this installation (same folder of code, same settings file, named `update-<date>-<time>`, whose record says the run ended well or went back), beyond `--keep <n>` (default 5), only after an update that worked. Never this run's, never one whose run needs the person, never a link, never anything else in the folder.
- **Same style as the scripts beside it.** `require-bash.sh` first [code: openbot/scripts/require-bash.sh:24], bash 3.2 syntax, no `set -e` (every step is checked and an exit trap prints the way back for any that was not), `scripts/start.sh` and `scripts/stop.sh` do the starting and stopping [code: scripts/start.sh:12] [code: scripts/stop.sh:9], and "does it answer" is the same question `start.sh` and `stop.sh` already ask [code: openbot/scripts/start.sh:415] [code: openbot/scripts/stop.sh:96]. `OPENBOT_ENV_FILE` is honoured, the scripts it runs are told about it, and the commands it prints name it, because a terminal opened later does not have it.
- **The script is in the checkout it moves.** A merge may replace `update.sh` while bash is reading it. So everything is a function and the last line leaves. Tested both ways: the move replaces the file with another version, and a fake install overwrites it in place after the move.

## 3. What is not built

- The notice in the app that a newer version exists (the next slice).
- The first update. A checkout older than the command does not have it, so that one has to be moved forward once by hand (`git pull --ff-only`, then `scripts/start.sh`). The docs say so.
- Updating by itself, on a schedule. The roadmap row says nothing is updated without the person's command.
- A copy of each Bot's own computer. Its profile and its workspace are Docker volumes with the Bot's files and logins; a stop removes the container and keeps them [code: openbot/supervisor/src/docker.ts:519]. The update leaves them alone and the copy does not include them (decision 3).
- A database that Docker does not start here. It is refused, not copied.
- A folder that is not a git checkout (an unpacked ZIP), and the desktop app's own folder [assumed: not a git checkout]. Refused.
- Anything the new version wrote before a go-back. Going back returns the database to the moment of the copy, by design.
- Going back when the old images are gone. `start.sh` builds them again from the old code [code: openbot/scripts/start.sh:602], which needs what a build needs [assumed].
- Windows without bash, and macOS bash 3.2 as shipped: not run [assumed to work].
- Two runs that find the same left-behind lock at the same moment. Taking it over is "remove, then make", which two runs can interleave. The wait for a lock that has no process number yet closes the common case (a run that has just made the folder), not that one.

## 4. Built so far

**How it was tested.** `update.test.ts` runs the script in a real git checkout, a clone of a bare repository made in a temporary folder, with two release tags and a commit after them. So every git decision in it is the real git's. Everything else the script runs is a fake on a PATH that holds nothing but the fakes and links to the real coreutils: `docker` (compose, `inspect` with the labels Compose puts on a container, and `psql`, `pg_dump`, `pg_restore` inside the postgres container), `bun`, `curl`, `sleep`, `df`, `stat`, `rm` (the real one, which can end the run on cue), and the checkout's own `scripts/start.sh` and `scripts/stop.sh`. The fakes keep a small model: a stack that is up or down, a database that is a few lines of text, a role password, who is connected, a watchdog that starts the stack after the Nth sleep, and, for a machine with two stacks, a second model in its own folder that the fakes pick by Compose project, as Compose does. `git` is a spy that records and runs the real one, and can be told to fail one subcommand.

The tests cover: what it is asked (bad options); the update that works, in order, for a branch, a tag, a detached checkout, `--main`, `--to`, `OPENBOT_ENV_FILE`, and a script replaced under it; the refusals, each of which must leave the checkout, the home folder and the model exactly as they were (compared before and after); `--check`; the copy (modes, contents, taken with nothing running, checked before the change); going back from every step from the stop on, in order; going back failing, with the printed commands run and shown to do the job; a watchdog at three moments; Ctrl-C at two, and while the database is being put back, and while old copies are tidied; the copy changed, unreadable or gone before it is restored from; whose postgres (another folder's, no labels, two containers, the shell and the settings file disagreeing) and two stacks of one checkout; the folder for the copies; `--to` with a stale local branch; a lock whose owner has not written its number yet; `--keep`; secrets.

- **Before and after.** On origin/main there is no `update.sh`, so all the tests fail there. The first version of the command passed its 80 tests. The review fixes below were each shown the same way: the 107 tests run against the first version of the command (the committed one, before the fixes) give 80 passes and 27 failures, and against the fixed one 107 passes. The 27 are 25 new tests and 2 old ones whose expectations changed (the plan, and the printed commands, which now check the copy). Two more new tests pass on both: they check that a valid label and a valid folder for the copies are still accepted. With the command, the whole file passes in about a minute (107 tests, 57 seconds in the last run).
- **Review fixes (same day).** (1) The copy is checked again right before the restore (section 2). (2) Whose postgres (section 2). Building its test found a defect in the first version: `setting()` asked the shell variable of the same name before the settings file, and the script had set `APP_PORT`, `SERVER_PORT` and `POSTGRES_PORT` to their defaults at the top, so ports in `.env`, `.env.eval` or the environment were never used (every earlier test used the default ports). A run for the second stack, whose ports are not the defaults, refused at the database check, and a person with other ports would have been checked on the wrong ones. Fixed: they are resolved in `main` (environment, settings file, default), and the two-stack tests assert which ports `curl` was asked about. (3) The plan says to pause anything that restarts FreeDuet by itself. (4) A Ctrl-C or an unexpected stop after the update worked is not a failed update. (5) The folder for the copies must be outside the repository. (6) `--to` and a stale local branch. (7) The lock. (8) A stop while the database is being put back says so.
- **Do they catch a defect?** 21 deliberate defects were put into `update.sh` one at a time (no refusal on local changes, a merge without `--ff-only`, a restore without `--create`, `.env` not put back, no wait for a watchdog, a secret printed, a go-back that exits 0, no quiet check before the copy or the move, a dump without `-C` or not private, the password not put back, `--keep` 50, the new stack not stopped before going back, `--check` going on, and others). 20 are caught by a test that names the behaviour. One is not: deleting this run's own copy from the removal list changes nothing, because the run's folder has no result line yet and is skipped for that reason too. The two protections overlap.
- **Checks.** `bash -n` and shellcheck (`-x -P SCRIPTDIR -s bash`, run here, not in CI) are clean on `update.sh`. Biome format and lint are clean on the whole of `openbot/`. `bun run typecheck:tests` is unchanged against its baseline, and `server/tests/assertion-shape.test.ts` passes (neither looks at the new test file: it is in `openbot/scripts/`, which has no type check). The new file type-checks on its own under the repository's strict base settings. All 457 tests of `openbot/scripts/` pass together, including the D39 guard in `start-restart-guard.test.ts`.
- **Not in the tests.** The tests prove the decisions and the order. They do not prove that a real Docker, a real `pg_dump`, a real `start.sh` or a real watchdog behave as the fakes do.

**NOT verified.** The command has NOT been run on a real installation: not against real Docker and the real postgres image, not with the real `start.sh` and `stop.sh`, not with a real `bun install`, not with a real watchdog, not on macOS or in Git Bash. The 75-second default wait is the documented minute plus a margin, and has not been measured on a real machine. The restore flags were checked once on a PostgreSQL 16 test cluster, not on a real FreeDuet database.

- **The final check proves less than it seems to.** It proves that the app and the API answer on their ports (`/api/capabilities` has the field only this server's payload has, and the app's page has its marker). It does not prove that the new version is the one answering: a stack of the old version that was left running, or another OpenBot on those ports, passes it. What keeps this from mattering is the order before it (the stop is checked, the stack is shown to be down, `start.sh` must finish). It is not tested against a real `start.sh` that fails to replace a running process.
- **The labels of a real Docker container.** The check of whose postgres it is reads three labels with `docker inspect`, and the tests give them as fakes. A Docker that records the folder in another form than the one `pwd -P` gives (a stack started from Windows while this runs in WSL, or a bind-mounted folder) would be refused as "another folder": that is the safe direction, and has not been tried [assumed].

**Where it differs from the first sketch of the task, and why.**

- The copy is made after the stop, not before (section 2). FreeDuet is down a few seconds longer; no write can be missing from the copy.
- `-C` on the dump and `--create` on the restore, instead of a plain `--clean --if-exists` (section 2).
- A fourth file in the copy, `role-password.sql` (section 2).
- Three options beyond the ones asked for: `--watch`, `--wait`, `--copies`.
- `--check` runs `git fetch --tags origin`. Without it it cannot say what the newest release is. If the fetch fails it says so and uses what is already downloaded.
- Ctrl-C after the stop exits 20 and prints what to run. It does not start a go-back by itself while the person is at the keyboard.
- A run interrupted or refused before any copy exists leaves no folder behind.

## 5. Decisions left to the maintainer

| 1. Where the copies go | (a) `~/.freeduet/updates` (built); (b) `openbot/.logs/`, beside the adopt backups | (a) | A copy must outlive the checkout and survive a `git clean`. It is still on the person's computer and private. `--copies` moves it |
| 2. How long to wait for a watchdog by default | (a) 75 seconds (built); (b) 0; (c) 120 | (a), then measure on a real machine | It adds 75 seconds to every update, also on a computer with no watchdog, because the wait ends early only when the stack comes back.
