# M1 technical plan: the team on your login

How M1 (issues #10 to #21 and #24) is built. Written from a map of OpenBot's remote-agent protocol made on 2026-11-08; file references are to `openbot/`. Read with [ARCHITECTURE.md](ARCHITECTURE.md) §3 and [PROVIDERS.md](PROVIDERS.md).

## 1. Shape

```
OpenBot server ──AG-UI POST /──────────────► agent-freeduet (Python, port 4230, one service for all ten members)
   ▲   (tools in RunAgentInput.tools,              │  reads the member's prompt from agents.yaml by forwardedProps.openbotBotId
   │    member id in forwardedProps)               │  runs: claude -p (official CLI, the person's own login, no built-in tools)
   │                                               │        └─ MCP server "freeduet" (stdio) = the tools OpenBot offered
   │◄── TOOL_CALL_* + RUN_FINISHED ────────────────┘  a tool call ends the segment; OpenBot runs it (grants, policy, approval gate, audit)
   └── next POST with the tool result ─────────────►  a fresh, stateless claude -p continues from the full transcript

OpenBot server ──Anthropic POST /v1/messages─► agent-freeduet: the server's own short model calls (titles, routing, tool selection,
                 (ANTHROPIC_BASE_URL)              auto-review, triage, voice summary), text only, routed by purpose
```

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Members are `remote-ag-ui` agents whose endpoint is exactly `MANAGED_AGENT_AG_UI_URL` (`http://localhost:4230/`) | Only that URL gets `x-openbot-agent-token` (`server/src/agents/managed-endpoint.ts`); one endpoint may serve many agent ids |
| D2 | `agents.yaml`: `type: ${FREEDUET_MEMBER_TYPE:-remote-ag-ui}`, `endpoint: ${MANAGED_AGENT_AG_UI_URL:-}`, and `system_prompt` kept | `FREEDUET_ROUTER=off` is `FREEDUET_MEMBER_TYPE=built-in` (precedent: `examples/fintech/agents.yaml`). The prompt stays in one file; agent-freeduet reads it by id |
| D3 | The member is identified by `forwardedProps.openbotBotId` alone, and a run without it is refused. This Bot's standing role (`standing-role:<id>`) is accepted wherever it is in `messages`; its prompt is the `agents.yaml` row, else that role. A standing role or holdings row naming another Bot (`standing-role:<other>`, `granted-tools:<other>`) never joins the system prompt: it is quoted as context at the top of the conversation | Neither URL nor body carries an agent id. The bot id is set by OpenBot's own middleware (`copilot.ts`, runWith) and reaches agent-freeduet only over the token-checked managed endpoint. The role is not always first: on a hop, middleware inside the one that adds it puts `openbot:personal-memory` and `openduet:channel` in front, and since #33 a browser chat's clone carries them too (`toolkit/src/copilotkit/agents.ts`); each is said once. The old `messages[0]` check refused every hop (fixtures `agent-freeduet/tests/fixtures/handoff_*_run.json`, recorded by `server/tests/freeduet-handoff.test.ts`) |
| D4 | **Tools stay in-band.** OpenBot's offered tools (`RunAgentInput.tools`) become the MCP server's tools. When the CLI calls one, agent-freeduet emits `TOOL_CALL_START/ARGS/END`, then `RUN_FINISHED`, and stops the CLI. OpenBot executes the call with its own approval gate and POSTs again with the result | This is the only path where approvals can pause and resume (`toolkit/src/headless-tools.ts`). The callback route can never wait for an approval and refuses instead (`server/src/approvals/types.ts:308-317`) |
| D5 | Only names in `forwardedProps.openbotDeploymentTools` go to `POST /api/agent-tools/call` with `AGENT_TOOL_TOKEN` and `forwardedProps.openbotRun`; their result goes straight back to the CLI. For FreeDuet's own members that list is `ask_person` only: the server runs their `message_bot` in-band like any other tool (`server/src/freeduet/coordination.ts`). If the callback refuses a hand-off only because the person has to be asked, agent-freeduet ends the segment and asks the person for that hand-off (who and what) in the conversation | That route exists for them (`server/src/app.ts:1842`), but it can never ask the person: an `ask` from the approval gate there is refused, and with auto-review on (OpenBot's default) the reviewer is shown no request at all, because the route carries no conversation. Iris's hand-off to Penny was refused that way. In-band, the gate reads the conversation and a pending approval suspends the run (D4) |
| D6 | **Stateless segments.** Every POST starts a new `claude -p --no-session-persistence` with the member prompt and the whole conversation rendered from `messages` (system rows, user, assistant, tool calls and results). No CLI session is resumed | Approval resumes arrive as a new run after the CLI is gone, restarts lose nothing, and segments are uniform. Costs more tokens per turn; optimise in M3 with continuity checkpoints |
| D7 | CLI lockdown, verified against the installed CLI's `--help`: `-p --output-format stream-json --verbose --include-partial-messages --no-session-persistence --tools "" --strict-mcp-config --mcp-config <freeduet only> --disable-slash-commands`, MCP tools pre-allowed (`--allowedTools mcp__freeduet`), `--append-system-prompt` for the member prompt and OpenBot's system rows; the conversation on stdin | No file, shell or web access except through OpenBot's gateway; no other MCP server; no permission prompts in a headless CLI (approvals are OpenBot's) |
| D8 | An SSE comment (`: keepalive`) every 15 s while the CLI works | OpenBot ends a turn after 60 s of silence (`AGENT_STALL_TIMEOUT_MS`) |
| D9 | The CLI's sign-in lives in a named volume mounted as the CLI's config directory. The person signs in once with `docker compose exec -it agent-freeduet claude`. **No FreeDuet code reads that directory** (test M1.8) | PROVIDERS.md rule 1 |
| D10 | Server-side model calls: `BOT_PROVIDER=anthropic`, `ANTHROPIC_BASE_URL=http://localhost:4230`, `ANTHROPIC_API_KEY=$FREEDUET_LOCAL_KEY` (a random key start.sh writes; agent-freeduet requires it in `x-api-key`). agent-freeduet's `POST /v1/messages` answers text-only requests and routes by purpose: auto-review (`approvals/policy.ts`) on a tier A engine; titles, routing, tool selection, triage and voice summaries on the free assistants chain, falling back to Claude Code. Purpose is recognised from each caller's fixed prompt markers, with a test per marker | Zero changes to the server's call sites; the server needs no real API key (docs/SERVER_MODEL_CALLS.md) |
| D11 | Engines: `engines.yaml` loaded and validated; the chain is always ordered subscription, then free, then metered; metered never runs while `metered.enabled` is false or a cap is 0. M1 implements the `claude-code` engine and the `openai-compatible` engine for free assistants (Ollama); the others are declared and refuse clearly | M1.7 |
| D12 | Not signed in, or a subscription limit: `RUN_ERROR` with code `OPENBOT_MODEL_AUTH_REQUIRED` for sign-in, and a plain message for limits | OpenBot records the first as a sign-in failure |
| D13 | Work reports and checkpoints (M1.13): after each segment agent-freeduet saves a checkpoint with AI Continuity's writer (MIT, attributed) under `/data/handoff/<botId>/<threadId>/` in its own volume | The member computers are other containers; one place to read on an engine switch |

| Need | Already in OpenBot | Missing |
|---|---|---|

| Memory of the work | Checkpoints (M1.13, D13) | Nobody reads them back until M3 |
| Memory of the team (what one member learned that others need) | None | Lessons (D16) |

Shared rule: when Iris did not ask for the work and the outcome is failed, blocked or needs you, the member also sends its report to Iris with `message_bot` | Iris sees every outcome, also of work she did not hand out. The tool reads FreeDuet's own data only, never the person's apps |
| D16 | **Lessons.** Iris may propose a lesson for a member ("Penny: check the VAT number before drafting an invoice"), with the evidence. A lesson is stored `pending` in `/data/lessons/<member>.json` and becomes `active` only after the person approves it in chat; a Bot's message never approves one. agent-freeduet adds that member's active lessons to its prompt on every run. The person can list, change and remove lessons by asking Iris. A failure with the same cause twice in seven days makes Iris ask Leo for a proposal to change the member's prompt or skills; applying it stays with the person | Corrections that last, never silent: a permanent change in behaviour is the person's decision |

| D18 | **Report guard.** When a segment ends a turn that did work (a tool call in the turn, an attached file, or a message that is neither just a greeting nor ends with a question: the shared no-report rule) and its text has no report, agent-freeduet runs one more `claude -p` with no tools at all, the conversation so far and a fixed instruction to write only the six lines from what the conversation shows; a complete report is streamed as the end of the same message, anything else adds nothing. The last thing I tried was <tool name>. A live run of jules-3 ended a booking turn with no text at all after a failed click: the app's handler had thrown, the SDK ran no follow-up (fixed in the app and the runner, `docs/UPSTREAM_TOUCHES.md`), and agent-freeduet had no answer of its own for an engine that says nothing |

## 6. Conversations and memory without CopilotKit Intelligence (#42)

Added on 2026-11-08 at the maintainer's request. Before #42, OpenBot refused to start without the three `INTELLIGENCE_*` settings (`openbot/server/src/config.ts`), so every FreeDuet install needed a CopilotKit account.

| # | Decision | Why |
|---|---|---|
| D20 | **CopilotKit Intelligence optional, off by default.** `FREEDUET_INTELLIGENCE=off` or `on`. Unset is upstream OpenBot, unchanged. With `off` the server boots with no `INTELLIGENCE_*` key, keeps conversations, history and memory in FreeDuet's own Postgres, and sends nothing to CopilotKit. Telemetry is off unless `COPILOTKIT_TELEMETRY_DISABLED=false` is set. With `on` the server needs the three keys, as upstream | FreeDuet promises self-hosted, zero cost and no API key. Intelligence keeps its own copy of every thread, user memory, browser trajectory and product analytics. Its free hosted tier (1,000 interactions per organization per month) would stop a real user quickly. CopilotKit's docs say the TypeScript runtime works without Intelligence; OpenBot made it mandatory |

How the default is chosen: `scripts/start.sh` writes `off` into a new `.env`. An existing `.env` with all three Intelligence settings and no `FREEDUET_INTELLIGENCE` line gets `on`, with a notice printed, so an install from before #42 keeps its conversations in Intelligence.

Measured in #45: with `off` and no telemetry variable, a boot, a chat turn, a headless turn, a hop and memory create and recall sent zero requests to any `*.copilotkit.ai` host. With `COPILOTKIT_TELEMETRY_DISABLED=false` the same probe does see telemetry, so the probe can see requests at all.

FreeDuet's own migrations live in `openbot/server/src/freeduet/threads/migrations/`, with their own journal and bookkeeping table, `freeduet_thread_migrations`. They are recorded by name and hash, run in one transaction behind an advisory lock, and are safe when two processes boot at once. An applied migration whose file has changed is refused.

| Table | Holds |
|---|---|
| `freeduet_threads` | One row per conversation: thread id, user, agent, name, times |
| `freeduet_thread_runs` | One row per run: run id, parent run, status (`running`, `finished`, `stopped`, `failed`, `interrupted`), the run's events compacted as `jsonb`, what the run was asked, and the runner that wrote it |
| `freeduet_thread_locks` | One row per thread while a run holds it: run id, user, agent, expiry. An expired lock is taken over |

Messages are not stored in a table of their own. They are rebuilt from the runs' events with AG-UI's own reducer.

Limits with `off`:

- Conversations already in Intelligence are not imported. An importer is a possible later phase.
- Switching from `off` to `on` starts fresh. Neither side copies the other's conversations.
- Memory is local. Recall is a text match, not a semantic search.
- Learned skills are off.
- Live tail (following a run that is still going, after a reload or from another tab) works in one server process only. FreeDuet supports one replica.
- A server restart in the middle of a run marks that run `interrupted` and keeps the text it had written.
- Keys and Learning variables left in `.env` are ignored, and the boot log names them once.

## 7. Gmail and Calendar with an app password (D24)

Added on 2026-11-10. The OAuth way to connect Gmail and Google Calendar (`google-workspace`) needs a Google Cloud project, an OAuth client, a public address for the consent screen to return to, and, for a person outside a Workspace domain, either a 7-day expiry (an app in testing) or Google's security assessment (CASA) for the Gmail scopes. That is a lot to ask of one person with one mailbox, on a project that promises a simple self-hosted install.

| # | Decision | Why |
|---|---|---|
| D24 | **A second, simpler way to connect Gmail and Calendar, next to the OAuth one.** A new catalogue entry, "Gmail and Google Calendar (app password)", key `google-imap`, auth kind `user-secret`, transport `google-imap`. The person pastes three things on their own connection page: their Gmail address, a Google app password (`myaccount.google.com/apppasswords`) and, optionally, the calendar's secret address in iCal format. Mail goes over IMAP and SMTP, the calendar over the iCal address. The OAuth entry is unchanged and both can be connected at once. **The same five tools** as the OAuth entry, with the same names, arguments and JSON answers and the same read and write lists (`gmail_search_messages`, `gmail_read_message` and `calendar_list_events` read; `gmail_send_reply` and, since the amendment below, `gmail_send_message` write, so each waits for the person's approval, apart from the one case D27 names); a test runs both adapters on the same fixtures and compares the answers. **Hosts are pinned in code** (`mail-presets.ts`): `imap.gmail.com:993` and `smtp.gmail.com:465`, both TLS, and a calendar address only from `https://calendar.google.com/calendar/ical/`. Any other host, a non-https address or a redirect off that host is refused; the catalogue row's address is never dialled. **Read-only mail**: the mailbox is opened with `EXAMINE`, bodies are fetched with `BODY.PEEK`, there is no tool that moves, deletes, labels or flags, and a test drives the real `imapflow` against a fake IMAP server and checks every command on the wire. Search is Gmail's own (`X-GM-RAW`, default `in:inbox newer_than:1d`), ids are the hex of `X-GM-MSGID` and `X-GM-THRID` (the ids the REST API uses), and the caps and timeouts are the REST adapter's. **A reply stays in its thread**: `In-Reply-To` and `References` come from the original, the subject is the one the Bot gives, with "Re:" added when it is missing, and the recipients are limited to people already on it; no new recipient can be added. A new recipient is only reachable through `gmail_send_message` (amendment below), which is a different tool with its own approval. **All three values are secrets**, stored together as one encrypted value of a new credential kind, `mcp_user_secret` (migration 0068), per person. They are never logged, never in an audit row, never in an error sentence and never returned: the status shows the address and whether a calendar is attached. Saving checks them first (one IMAP login, and one fetch of the calendar if an address was given) and stores nothing unless they work; a wrong password gets a fixed sentence that repeats nothing that was typed. Disconnecting revokes the stored value here at once, and removing the connector or the person revokes it as well. A test runs the real gate and holds this | Gmail is where most people's mail and calendar are, and an app password is the only way to reach it without a Google Cloud project. IMAP and SMTP are standard and Gmail's extensions (`X-GM-RAW`, `X-GM-MSGID`, `X-GM-THRID`) give the same search, ids and threads the REST adapter returns, so the Bots, the morning brief and the setup checklist work on either connection without being taught a second shape. ### D24 amendment, 2026-11-12: a fifth tool, `gmail_send_message`

- **Arguments.** `to` (one to five plain addresses, no display name), `subject` (one line, at most 200 characters) and `body` (plain text, at most 20,000 characters). The answer is `{"sent":true,"id":"","threadId":""}`, the reply's shape; the OAuth adapter fills the ids Gmail gives. A recipient Gmail refuses is reported with "The email went to the others."
- **A write in the catalogue for both entries.** `writeTools` is `["gmail_send_reply", "gmail_send_message"]` on `google-workspace` and on `google-imap`; a recorded "read" cannot narrow it, as for the reply. Background runs (a check-in, research) are never offered it, because they are limited to reads.
- **Asked about every time.** Unlike a reply, "Always allow" is neither offered nor honoured for a new email: it is opened as a request with the policy `always_ask`, the approval store refuses `allow_always` for it, a saved rule for the same address does not answer it, and the app hides the button. A standing answer for one address must never send a later, different email. The card shows every recipient, the subject and the whole body (folded behind "Show all N characters" when long, never cut); the chat-channel card is bounded and says so ("Not all shown").
- **Who has it.** Only Otto, through the new skill `send-a-new-email` (`examples/freeduet/skills.yaml`); the grant of the tool is an administrator's, as for every connector tool, and is not seeded. Iris, Penny and every other member are not offered it. Otto's prompt says a reply goes through `gmail_send_reply` and a new email through `gmail_send_message`, that an address is used exactly as written (never invented, corrected or completed, and asked about when it looks wrong), and that after sending he says plainly that it was sent, to whom, its subject and the text. Iris hands the request to Otto instead of refusing.
- **When it needs no card at all**, see D27 below.

| # | Decision | Why |
|---|---|---|
| D25 | **A local Whisper, optional, off by default, switched on by one line in `.env`: `FREEDUET_DICTATION=local`.** (1) **A `whisper` service** in `docker-compose.yml`, behind the profile `whisper` so nothing starts or builds without the flag. How to run them is in `openbot/docs/configuration.md`, "Local Whisper" | An app for people who are not developers cannot start with "get an API key". A local model is the only way to promise that a recording never leaves the machine, and whisper.cpp is the smallest runtime that serves the OpenAI path, so the adapter, the route, the limits and the composer did not have to change. The model is pinned by hash because a download over the network is the one thing in this design that runs unreviewed bytes; the tag is pinned by commit for the same reason. The flag is off because a model of 574 MB and a container are not a thing to install by surprise, and a person who set up their own service keeps it. Limits:

- **CPU only in v0.1.** The image is built for the computer that builds it and uses no GPU. How long a request takes is what 7a reports on the maintainer's computer; it is not guessed here.
- **A recording is at most 120 seconds**, as for every provider, and one transcription per person at a time. A long dictation on a slow computer can pass the 60 seconds the route allows a provider and then fails with the existing "timed out" message.
- **A phone needs https.** On `http://<computer>:3010` the browser offers no microphone. The two ways out (use the computer itself, or put the app behind https) are in the configuration guide; neither is built.
- **The whisper port has no sign-in.** It is on loopback only, but anything running on that computer can reach it, and whisper-server answers any origin (`Access-Control-Allow-Origin: *`, `server.cpp:739`). What a caller can do: send it audio and read the transcript (that costs CPU time and exposes nothing the caller did not already hold), and `POST /load` (`server.cpp:1175-1210`) with the path of a file in the container, which makes the server drop its model and, when the file is not a model, `exit(1)`, so the service stays down until `start.sh` is run again. Nothing is read back from the container's files. A web page in the person's browser needs to get past the browser's own protection of local addresses to do any of this. It stays as it is until a request is made to put the service anywhere but loopback, and that should come with a token. Whisper.cpp v1.9.5 has no option to turn `/load` off.

### D25 amendment, 2026-11-11: measured on the maintainer's computer

First real run (32 threads, 61 GB, `large-v3-turbo-q5_0`, no language sent): word error rate **2.9%** on 100 FLEURS clips, no failed request, but **17.26 s** median and 20.85 s at the 95th percentile per request, and 7c failed ("Thank you." on digital silence, "." on room noise). The service log said `n_threads = 4 / 32`. What changed, from the source at v1.9.5:

- **Threads.** The server takes `min(4, hardware threads)` (`examples/server/server.cpp:73`, `--threads` at :210, applied at :936). The service now takes `WHISPER_THREADS`, by default half of `nproc` clamped to 4..16 (`openbot/whisper/threads.sh`, tested). Whether 16 is the best number for a given computer is for the maintainer to measure with the override.
- **Decoding.** The server is already **greedy** unless `beam_size > 1` (default -1, :82; strategy chosen at :927; `best_of` 2 at :81 only matters on the temperature fallback). So beam search was not the cause of the slowness and stays off; `WHISPER_BEAM_SIZE` (`--beam-size`, :218) lets the maintainer measure it without a rebuild. Temperature fallback (`temperature_inc` 0.2, :89) can only be switched off by a request field (:582): the server's `--no-fallback` is parsed (:228) and never used. It is not touched, because turning it off is a quality trade nobody has measured.
- **Silence, (a) options.** The server and library offer `--suppress-nst`, `--no-speech-thold` (:247) and `--logprob-thold` (:222), but a segment is dropped only when both the no-speech and the log-probability conditions hold (`src/whisper.cpp:7780`), and `logprob_thold` also drives the fallback re-decoding, so raising it is not a clean silence control. Not used.
- **Silence, (b) the response (tried, replaced).** `response_format=verbose_json` gives each segment `no_speech_prob` (`server.cpp:1154`). It was built and measured, and the service reports 0.000 on every segment, silence included, so a filter on it cannot work. Removed; see the second amendment.
- **7b** uses the ffmpeg in the built whisper image through `docker run` (no network, no capabilities, the caller's user, one folder mounted) when the host has none.

### D25 second amendment, 2026-11-11

Measured with 3348a56 (16 threads): 100 clips, language detected: `large-v3-turbo-q5_0` WER 2.8%, median 9.78 s, p95 17.42 s, 783 MB; `large-v3-turbo` 2.9%, 8.01 s, 8.79 s, 1.75 GB; `small` 7.9%, 1.83 s. Threads (q5_0, 30 clips): 8 gave 14.14 s, 16 about 9.8 s, 32 10.92 s, so the cap of 16 stays. At 4 threads, detection 17.26 s against 8.64 s with `it`, same 2.9%. 7b passed (wav, webm/opus and mp4/aac all 2.1%, through the image's ffmpeg). 7c failed again, with `no_speech_prob` 0.000 everywhere.

- **VAD on for the local service.** Hand-run by the maintainer on the same image, `--language it`: without VAD, 5 s and 30 s of silence gave "Grazie a tutti.", noise "Grazie."; with `--vad --vad-model ggml-silero-v5.1.2.bin` all four were empty, 2 s of speech kept, a full clip and a clip followed by 10 s of silence kept, WER on 30 clips 1.1% against 1.4% without, median 10.3 s against 8.7 s. The entrypoint passes `--vad --vad-model` (`server.cpp:260-261`, applied at :968-976) unless `WHISPER_VAD=off`. The VAD options stay at the server's defaults, none exposed: threshold 0.5 (:125), minimum speech 250 ms (:126), minimum silence 100 ms (:127), no maximum speech (:128), padding 30 ms (:129), overlap 0.1 (:130). The server's own default is VAD off (:123).
- **The VAD model is pinned like the Whisper ones**: `ggml-silero-v5.1.2.bin`, 885098 bytes, sha256 `29940d98d42b91fbd05ce489f3ecf7c72f0a42f027e4875919a28fb4c04ea2cf`, from https://huggingface.co/ggml-org/whisper-vad, read from the file's Git LFS pointer (`/raw/main/ggml-silero-v5.1.2.bin`) on 2026-11-11 and equal to what the maintainer's download gave. Fetched with the same checksum-verified code (`openbot/whisper/fetch-model.ts --vad`). Its licence is not recorded in NOTICE.md yet: the Silero VAD project is MIT, to be confirmed against the repository's model card.
- **A caution from Dictatum** (a dictation app made by the same group as FreeDuet; more about it later), as the coordinator relayed it: VAD together with a vocabulary prompt on dictation with long pauses can cut speech. Not reproduced here (the pause case below is the guard), which is why `WHISPER_VAD=off` exists and the prompt is optional.
- **The no-speech filter and the verbose request are gone.** The local adapter is back to the plain request; `joinSegments` stays because VAD output still has line breaks between segments.
- **7c guards the other way, with whole clips.** Besides the four silent cases: 2 s of speech then 10 s of silence still returns words of the sentence. The 2 s start at the speech onset (the first 20 ms window whose RMS is above 5% of the clip's own peak), 100 ms before it, and at least 1 s of them must be above that level, else the next cached clip is used: the first 2 s of a FLEURS clip are mostly lead-in silence, which VAD rightly drops. One more row, "a short word: 0.6 s from the onset, then 3 s of silence", is measured only: printed, never failing; one clip with a 3 s pause inserted in its middle is no more than 2 WER points worse than the clip alone; two whole clips with 5 s of silence between them and 3 s after return at least half of the words of each sentence. A clip cut mid-word proves nothing, so none is used.
- **Language is told, not detected.** Order: `TRANSCRIPTION_LANGUAGE`; else the browser's primary language subtag sent with the recording (the app has no language setting of its own: no i18n, no per-person preference), accepted only if it is exactly one of Whisper's two-letter codes, else dropped; else detection. Local service only: other providers ignore the hint, so their request is unchanged. Limit: a person whose browser is not in the language they dictate must set `TRANSCRIPTION_LANGUAGE`.
- Default model unchanged (`large-v3-turbo-q5_0`); the measured table is in `configuration.md` for the maintainer to choose from.

## 10. A new email goes out on the person's own written request (D27)

Added on 2026-11-12, by the maintainer's explicit decision while D24's fifth tool was being built: when he writes "write to <address>", it must do it. He has already approved by writing it, and a second card asking the same thing is noise. The decision covers `gmail_send_message` only. `gmail_send_reply` is exactly as it was, and nothing else about an account action changes.

| # | Decision | Why |
|---|---|---|
| D27 | **A new email is sent without a card when, and only when, every one of these holds, checked on the server at the approval gate and never from what the model says about itself; in every other case it waits for the person.** (1) **The run is the person's own live chat turn.** The run carries no initiator, which is what a turn started from the app carries. A routine, a check-in, a memory run, the deployment, a task, a message delivered from another channel, a group conversation, the continuation after another approval and every hand-off carry an explicit initiator and fail this condition (`typed-recipients.ts`, `recipientsTypedByPerson`, called from `plugin-store/calls.ts`). (2) **The message is recent: the latest message the person typed in that conversation, the one that started the turn, and no other (a window of one).** An earlier message cannot be told from a routine's stored prompt or a check-in's text that now sits in the same history, so none is trusted. (3) **Every recipient is one whole word of that message**, equal ignoring case and surrounding spaces. A message that is not plain text (attachments are a list of parts), is longer than 600 characters (a paste, the commonest way for somebody else's words to reach a message the person sent), is a hand-off's envelope (`handoff-` id), or has another role (a Bot's text, a tool result, mail, a page, memory) is never looked at. A recipient that only appears inside a longer address, on another domain, with an added dot or a look-alike letter, or that the member corrected or completed ("x@gmail.co" typed, "x@gmail.com" sent), is a different string and asks. A recipient beyond those typed asks. **Subject and body are the member's own words and are not matched;** the caps and the validation of D24's amendment still apply. **Everything else still asks**, with the whole email on the card: an address from an email, a page or a tool result, a corrected or completed address, an extra recipient, a routine, a check-in, a hand-off, a turn the server started, an address typed in an earlier message, and a deployment with no way to ask (it refuses, nothing is sent). **After a send without a card the member says plainly that it was sent, to whom, its subject and the text** (Otto's prompt and skill). **One send per request:** the same email (person, run, recipients, subject, body) is tried once per run, a failure included, because a half-delivered send must not go to the others twice; a repeat is refused with "Not sent again". The audit row for such a send says `approvedBy: person_request`. The person's own "ask before making changes" setting and any team rule that asks still open a card as for any write | "The person's own written request is the approval." Asking again what the person has just written is the kind of friction a personal assistant should not have, and the person already sees, in their own words, who it goes to. What the rule never does is take the Bot's word for it: the server reads the conversation it holds, and the only thing that can stand in for the card is something a person typed to start this very turn. Delegation must never launder an account action, so a Bot writing an address into a brief, a memory or a stored prompt is not "typed by the person", and any doubt resolves to asking |

### Amendment (2026-11-12): the person asks Iris, and Iris hands the email to Otto (D27a)

The maintainer talks to Iris, not to Otto, so "send an email to ana@example.com saying good morning" always reached Otto as a hand-off and always cost a card in a scratch thread he never sees. D27a lets it go out with no card **when the server itself can show that the hop came from the person's own typed message, and only then.** Nothing the model writes can set, change or read what the server relies on.

| # | Decision | Why |
|---|---|---|
| D27a | **The mark.** When a member calls `message_bot` during the person's own live chat turn (the run's continuation carries no initiator, exactly D27 condition 1), the server records on the hop's own queue row, beside the envelope and never inside it, who the person is, which conversation and run the hop was made in, and the id and a SHA-256 of the person's latest typed message of that turn (`agents/handoff-request.ts`, `handedRequestOf`, called from `agents/handoff-tool.ts`). It is computed from the signed run assertion and the run's own input messages. The tool's arguments, the brief and the constraints are not parameters of it, and a `request` key a model puts in them is ignored. A hop made from inside a hop, from a routine, a check-in, a memory run, the deployment, a task, a delivered message or a group conversation gets no mark; neither does a relay or a notice, which are built elsewhere with no origin. **The load.** At the approval gate, when the member who received the hop calls `gmail_send_message`, the server verifies the run assertion it signed (the member, the person, one hop deep), finds the hop's row by the claim the assertion names, checks the row is still leased to this run, addressed to this member and this person and not a relay, checks the mark names this person, this hop's conversation and this hop's run, and then reads the ORIGIN conversation itself and takes the person's latest message there. That message must still be the one the mark names (same id, same text hash). It is then given to the same pure rule as D27, `recipientsTypedByPerson`: one message, a plain string, at most 600 characters, every recipient a whole word of it ignoring case, one to five plain addresses. The receiver's own history is never consulted. **The limits, each held by a test through the real gate:** one hop only; the mark is good only for the hop made in that turn and only while that turn is still the person's latest message in the origin conversation (a newer message, or a hop left over from an earlier turn, asks); the same person on both sides; a brief that names an address the person did not type asks; a member that changes the address asks; an extra recipient asks; a call that claims to be the person's own still asks; a conversation that cannot be read asks; **one send per person's message:** the same email (person, origin message, recipients, subject, body) goes out once however many hops were made from it, a failure included, and a repeat is refused with "Not sent again". The audit row says `approvedBy: person_request`. The person's own "ask before making changes" setting and any team rule that asks still open a card | The person's own written request is the approval, and it does not stop being theirs because they wrote it to the head of the team. What would be wrong is trusting the hop's text, so the server decides from three things only it holds: its own signed assertion, its own queue row, and the conversation it stores. Any doubt resolves to asking |

**After a send with no card, the person is told.** Otto's prompt already says to tell them that it was sent, to whom, its subject and the text. Iris's "How you handle results" now says the same when a colleague reports an email sent, and that her three-sentence chat limit does not cut it short, so the answer the person reads from Iris says it plainly.

**What is not verified, and what would change it.**

- **Not run end to end on a live stack.** The conditions are proved by tests through the real gate, the real queue rows and the real thread store (`send-message-approval.integration.test.ts`, `handoff-request.integration.test.ts`, `handoff-request.test.ts`), with a fake mail backend. No eval was added: the eval stack has no Gmail. Whether the person's message is already readable in the origin conversation while Iris's turn is still running depends on the thread store reading the running turn (`threads/store.ts`, `getThreadMessages`, which includes the live run); a deployment where it is not readable fails to the card.
- **A built-in (in-process) Bot** gets no hand-off claim on its run assertion, so a hop to it asks. Only the remote members that FreeDuet runs through agent-freeduet are covered.
- **A shared channel's other members.** The conversation holds messages by several people in a channel; the origin message is whatever the conversation stores as the person's latest, the same limit the direct rule has.
- **"Once per message" is in the server's process** (like "once per run"): a restart forgets it.
- **The forward hop is a scratch thread.** When a hop does ask, its card is in the person's approval list and not in a conversation they are looking at; that is as before.
- **Subject and body are the member's**, as in D27: a hand-off brief can change what the email says, not who gets it.

**What is not covered, and what would be needed.**

- **A hand-off asks unless the server itself recorded where it came from.** The rule above is the direct case. A hand-off carries an explicit initiator and fails the direct rule, and the receiver's history holds a Bot's envelope, so the person's message cannot be read from it. The amendment below closes that case for one hop and nothing else; every hand-off that does not meet every condition of the amendment still asks.
- **The window is one message.** An address typed two messages ago asks again. A wider window needs the same provenance mark on each message, because role `user` also holds the server's own messages (a routine's prompt, a task's, a delivered one) with nothing to tell them apart in an old history.
- **What the person's words cannot show.** A message the person sent by tapping a suggestion a Bot wrote is still theirs, and an address inside a short paste in their own message counts. The card exists for every other case.
- **Subject and body are the member's.** A prompt injected through mail the member read in the same turn can change what the email says, not who gets it. Several different emails to the same typed address in one run are each sent (only an exact repeat is stopped); a per-run cap is a decision for the maintainer.
- **The "once per run" memory is in the server's process.** A restart forgets it, and a new run is a new request.
- Evals: the cases that say "any email goes through the send tool and its approval" (`iris-4`, `portia-3`) are about a member without the tool, or an address nobody typed, and still hold; no eval for a typed address was added, because the eval stack has no Gmail connected.

## 13. A connector connected before a tool existed learns the tool at start, and a tool is never granted by arriving (D30)
