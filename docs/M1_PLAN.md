# M1 technical plan: the team on your login

How M1 (issues #10 to #21 and #24) is built. Written from a map of OpenBot's remote-agent protocol made on 2026-11-08; file references are to `openbot/`. Read with [ARCHITECTURE.md](ARCHITECTURE.md) §3 and [PROVIDERS.md](PROVIDERS.md).

## 1. Shape

```
OpenBot server ──AG-UI POST /──────────────► agent-freeduet (Python, port 4230, one service for all ten members)
   ▲   (tools in RunAgentInput.tools,              │  reads the member's prompt from agents.yaml by forwardedProps.openbotBotId
   │    member id in forwardedProps)               │  runs: claude -p (official CLI, the person's own login, no built-in tools)
   │                                               │        └─ MCP server "freeduet" (stdio) = the tools OpenBot offered
   │◄── TOOL_CALL_* + RUN_FINISHED ────────────────┘  a tool call ends the segment; OpenBot runs it (grants, policy, approval gate, audit)
   └── next POST with the tool result ─────────────►  a fresh, stateless claude -p continues from the full transcript

OpenBot server ──Anthropic POST /v1/messages─► agent-freeduet: the server's own short model calls (titles, routing, tool selection,
                 (ANTHROPIC_BASE_URL)              auto-review, triage, voice summary), text only, routed by purpose
```

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Members are `remote-ag-ui` agents whose endpoint is exactly `MANAGED_AGENT_AG_UI_URL` (`http://localhost:4230/`) | Only that URL gets `x-openbot-agent-token` (`server/src/agents/managed-endpoint.ts`); one endpoint may serve many agent ids |
| D2 | `agents.yaml`: `type: ${FREEDUET_MEMBER_TYPE:-remote-ag-ui}`, `endpoint: ${MANAGED_AGENT_AG_UI_URL:-}`, and `system_prompt` kept | `FREEDUET_ROUTER=off` is `FREEDUET_MEMBER_TYPE=built-in` (precedent: `examples/fintech/agents.yaml`). The prompt stays in one file; agent-freeduet reads it by id |
| D3 | The member is identified by `forwardedProps.openbotBotId` alone, and a run without it is refused. This Bot's standing role (`standing-role:<id>`) is accepted wherever it is in `messages`; its prompt is the `agents.yaml` row, else that role. A standing role or holdings row naming another Bot (`standing-role:<other>`, `granted-tools:<other>`) never joins the system prompt: it is quoted as context at the top of the conversation | Neither URL nor body carries an agent id. The bot id is set by OpenBot's own middleware (`copilot.ts`, runWith) and reaches agent-freeduet only over the token-checked managed endpoint. The role is not always first: on a hop, middleware inside the one that adds it puts `openbot:personal-memory` and `openduet:channel` in front, and since #33 a browser chat's clone carries them too (`toolkit/src/copilotkit/agents.ts`); each is said once. The old `messages[0]` check refused every hop (fixtures `agent-freeduet/tests/fixtures/handoff_*_run.json`, recorded by `server/tests/freeduet-handoff.test.ts`) |
| D4 | **Tools stay in-band.** OpenBot's offered tools (`RunAgentInput.tools`) become the MCP server's tools. When the CLI calls one, agent-freeduet emits `TOOL_CALL_START/ARGS/END`, then `RUN_FINISHED`, and stops the CLI. OpenBot executes the call with its own approval gate and POSTs again with the result | This is the only path where approvals can pause and resume (`toolkit/src/headless-tools.ts`). The callback route can never wait for an approval and refuses instead (`server/src/approvals/types.ts:308-317`) |
| D5 | Only names in `forwardedProps.openbotDeploymentTools` go to `POST /api/agent-tools/call` with `AGENT_TOOL_TOKEN` and `forwardedProps.openbotRun`; their result goes straight back to the CLI. For FreeDuet's own members that list is `ask_person` only: the server runs their `message_bot` in-band like any other tool (`server/src/freeduet/coordination.ts`). If the callback refuses a hand-off only because the person has to be asked, agent-freeduet ends the segment and asks the person for that hand-off (who and what) in the conversation | That route exists for them (`server/src/app.ts:1842`), but it can never ask the person: an `ask` from the approval gate there is refused, and with auto-review on (OpenBot's default) the reviewer is shown no request at all, because the route carries no conversation. Iris's hand-off to Penny was refused that way. In-band, the gate reads the conversation and a pending approval suspends the run (D4) |
| D6 | **Stateless segments.** Every POST starts a new `claude -p --no-session-persistence` with the member prompt and the whole conversation rendered from `messages` (system rows, user, assistant, tool calls and results). No CLI session is resumed | Approval resumes arrive as a new run after the CLI is gone, restarts lose nothing, and segments are uniform. Costs more tokens per turn; optimise in M3 with continuity checkpoints |
| D7 | CLI lockdown, verified against the installed CLI's `--help`: `-p --output-format stream-json --verbose --include-partial-messages --no-session-persistence --tools "" --strict-mcp-config --mcp-config <freeduet only> --disable-slash-commands`, MCP tools pre-allowed (`--allowedTools mcp__freeduet`), `--append-system-prompt` for the member prompt and OpenBot's system rows; the conversation on stdin | No file, shell or web access except through OpenBot's gateway; no other MCP server; no permission prompts in a headless CLI (approvals are OpenBot's) |
| D8 | An SSE comment (`: keepalive`) every 15 s while the CLI works | OpenBot ends a turn after 60 s of silence (`AGENT_STALL_TIMEOUT_MS`) |
| D9 | The CLI's sign-in lives in a named volume mounted as the CLI's config directory. The person signs in once with `docker compose exec -it agent-freeduet claude`. **No FreeDuet code reads that directory** (test M1.8) | PROVIDERS.md rule 1 |
| D10 | Server-side model calls: `BOT_PROVIDER=anthropic`, `ANTHROPIC_BASE_URL=http://localhost:4230`, `ANTHROPIC_API_KEY=$FREEDUET_LOCAL_KEY` (a random key start.sh writes; agent-freeduet requires it in `x-api-key`). agent-freeduet's `POST /v1/messages` answers text-only requests and routes by purpose: auto-review (`approvals/policy.ts`) on a tier A engine; titles, routing, tool selection, triage and voice summaries on the free assistants chain, falling back to Claude Code. Purpose is recognised from each caller's fixed prompt markers, with a test per marker | Zero changes to the server's call sites; the server needs no real API key (docs/SERVER_MODEL_CALLS.md) |
| D11 | Engines: `engines.yaml` loaded and validated; the chain is always ordered subscription, then free, then metered; metered never runs while `metered.enabled` is false or a cap is 0. M1 implements the `claude-code` engine and the `openai-compatible` engine for free assistants (Ollama); the others are declared and refuse clearly | M1.7 |
| D12 | Not signed in, or a subscription limit: `RUN_ERROR` with code `OPENBOT_MODEL_AUTH_REQUIRED` for sign-in, and a plain message for limits | OpenBot records the first as a sign-in failure |
| D13 | Work reports and checkpoints (M1.13): after each segment agent-freeduet saves a checkpoint with AI Continuity's writer (MIT, attributed) under `/data/handoff/<botId>/<threadId>/` in its own volume | The member computers are other containers; one place to read on an engine switch |

| Need | Already in OpenBot | Missing |
|---|---|---|

| Memory of the work | Checkpoints (M1.13, D13) | Nobody reads them back until M3 |
| Memory of the team (what one member learned that others need) | None | Lessons (D16) |

Shared rule: when Iris did not ask for the work and the outcome is failed, blocked or needs you, the member also sends its report to Iris with `message_bot` | Iris sees every outcome, also of work she did not hand out. The tool reads FreeDuet's own data only, never the person's apps |
| D16 | **Lessons.** Iris may propose a lesson for a member ("Penny: check the VAT number before drafting an invoice"), with the evidence. A lesson is stored `pending` in `/data/lessons/<member>.json` and becomes `active` only after the person approves it in chat; a Bot's message never approves one. agent-freeduet adds that member's active lessons to its prompt on every run. The person can list, change and remove lessons by asking Iris. A failure with the same cause twice in seven days makes Iris ask Leo for a proposal to change the member's prompt or skills; applying it stays with the person | Corrections that last, never silent: a permanent change in behaviour is the person's decision |

| D18 | **Report guard.** When a segment ends a turn that did work (a tool call in the turn, an attached file, or a message that is neither just a greeting nor ends with a question: the shared no-report rule) and its text has no report, agent-freeduet runs one more `claude -p` with no tools at all, the conversation so far and a fixed instruction to write only the six lines from what the conversation shows; a complete report is streamed as the end of the same message, anything else adds nothing. The last thing I tried was <tool name>. A live run of jules-3 ended a booking turn with no text at all after a failed click: the app's handler had thrown, the SDK ran no follow-up (fixed in the app and the runner, `docs/UPSTREAM_TOUCHES.md`), and agent-freeduet had no answer of its own for an engine that says nothing |

## 6. Conversations and memory without CopilotKit Intelligence (#42)

Added on 2026-11-08 at the maintainer's request. Before #42, OpenBot refused to start without the three `INTELLIGENCE_*` settings (`openbot/server/src/config.ts`), so every FreeDuet install needed a CopilotKit account.

| # | Decision | Why |
|---|---|---|
| D20 | **CopilotKit Intelligence optional, off by default.** `FREEDUET_INTELLIGENCE=off` or `on`. Unset is upstream OpenBot, unchanged. With `off` the server boots with no `INTELLIGENCE_*` key, keeps conversations, history and memory in FreeDuet's own Postgres, and sends nothing to CopilotKit. Telemetry is off unless `COPILOTKIT_TELEMETRY_DISABLED=false` is set. With `on` the server needs the three keys, as upstream | FreeDuet promises self-hosted, zero cost and no API key. Intelligence keeps its own copy of every thread, user memory, browser trajectory and product analytics. Its free hosted tier (1,000 interactions per organization per month) would stop a real user quickly. CopilotKit's docs say the TypeScript runtime works without Intelligence; OpenBot made it mandatory |

How the default is chosen: `scripts/start.sh` writes `off` into a new `.env`. An existing `.env` with all three Intelligence settings and no `FREEDUET_INTELLIGENCE` line gets `on`, with a notice printed, so an install from before #42 keeps its conversations in Intelligence.

Measured in #45: with `off` and no telemetry variable, a boot, a chat turn, a headless turn, a hop and memory create and recall sent zero requests to any `*.copilotkit.ai` host. With `COPILOTKIT_TELEMETRY_DISABLED=false` the same probe does see telemetry, so the probe can see requests at all.

FreeDuet's own migrations live in `openbot/server/src/freeduet/threads/migrations/`, with their own journal and bookkeeping table, `freeduet_thread_migrations`. They are recorded by name and hash, run in one transaction behind an advisory lock, and are safe when two processes boot at once. An applied migration whose file has changed is refused.

| Table | Holds |
|---|---|
| `freeduet_threads` | One row per conversation: thread id, user, agent, name, times |
| `freeduet_thread_runs` | One row per run: run id, parent run, status (`running`, `finished`, `stopped`, `failed`, `interrupted`), the run's events compacted as `jsonb`, what the run was asked, and the runner that wrote it |
| `freeduet_thread_locks` | One row per thread while a run holds it: run id, user, agent, expiry. An expired lock is taken over |

Messages are not stored in a table of their own. They are rebuilt from the runs' events with AG-UI's own reducer.

Limits with `off`:

- Conversations already in Intelligence are not imported. An importer is a possible later phase.
- Switching from `off` to `on` starts fresh. Neither side copies the other's conversations.
- Memory is local. Recall is a text match, not a semantic search.
- Learned skills are off.
- Live tail (following a run that is still going, after a reload or from another tab) works in one server process only. FreeDuet supports one replica.
- A server restart in the middle of a run marks that run `interrupted` and keeps the text it had written.
- Keys and Learning variables left in `.env` are ignored, and the boot log names them once.

## 7. Gmail and Calendar with an app password (D24)

Added on 2026-11-10. The OAuth way to connect Gmail and Google Calendar (`google-workspace`) needs a Google Cloud project, an OAuth client, a public address for the consent screen to return to, and, for a person outside a Workspace domain, either a 7-day expiry (an app in testing) or Google's security assessment (CASA) for the Gmail scopes. That is a lot to ask of one person with one mailbox, on a project that promises a simple self-hosted install.

| # | Decision | Why |
|---|---|---|
| D24 | **A second, simpler way to connect Gmail and Calendar, next to the OAuth one.** A new catalogue entry, "Gmail and Google Calendar (app password)", key `google-imap`, auth kind `user-secret`, transport `google-imap`. The person pastes three things on their own connection page: their Gmail address, a Google app password (`myaccount.google.com/apppasswords`) and, optionally, the calendar's secret address in iCal format. Mail goes over IMAP and SMTP, the calendar over the iCal address. The OAuth entry is unchanged and both can be connected at once. **The same five tools** as the OAuth entry, with the same names, arguments and JSON answers and the same read and write lists (`gmail_search_messages`, `gmail_read_message` and `calendar_list_events` read; `gmail_send_reply` and, since the amendment below, `gmail_send_message` write, so each waits for the person's approval, apart from the one case D27 names); a test runs both adapters on the same fixtures and compares the answers. **Hosts are pinned in code** (`mail-presets.ts`): `imap.gmail.com:993` and `smtp.gmail.com:465`, both TLS, and a calendar address only from `https://calendar.google.com/calendar/ical/`. Any other host, a non-https address or a redirect off that host is refused; the catalogue row's address is never dialled. **Read-only mail**: the mailbox is opened with `EXAMINE`, bodies are fetched with `BODY.PEEK`, there is no tool that moves, deletes, labels or flags, and a test drives the real `imapflow` against a fake IMAP server and checks every command on the wire. Search is Gmail's own (`X-GM-RAW`, default `in:inbox newer_than:1d`), ids are the hex of `X-GM-MSGID` and `X-GM-THRID` (the ids the REST API uses), and the caps and timeouts are the REST adapter's. **A reply stays in its thread**: `In-Reply-To` and `References` come from the original, the subject is the one the Bot gives, with "Re:" added when it is missing, and the recipients are limited to people already on it; no new recipient can be added. A new recipient is only reachable through `gmail_send_message` (amendment below), which is a different tool with its own approval. **All three values are secrets**, stored together as one encrypted value of a new credential kind, `mcp_user_secret` (migration 0068), per person. They are never logged, never in an audit row, never in an error sentence and never returned: the status shows the address and whether a calendar is attached. Saving checks them first (one IMAP login, and one fetch of the calendar if an address was given) and stores nothing unless they work; a wrong password gets a fixed sentence that repeats nothing that was typed. Disconnecting revokes the stored value here at once, and removing the connector or the person revokes it as well. A test runs the real gate and holds this | Gmail is where most people's mail and calendar are, and an app password is the only way to reach it without a Google Cloud project. IMAP and SMTP are standard and Gmail's extensions (`X-GM-RAW`, `X-GM-MSGID`, `X-GM-THRID`) give the same search, ids and threads the REST adapter returns, so the Bots, the morning brief and the setup checklist work on either connection without being taught a second shape. ### D24 amendment, 2026-11-12: a fifth tool, `gmail_send_message`

- **Arguments.** `to` (one to five plain addresses, no display name), `subject` (one line, at most 200 characters) and `body` (plain text, at most 20,000 characters). The answer is `{"sent":true,"id":"","threadId":""}`, the reply's shape; the OAuth adapter fills the ids Gmail gives. A recipient Gmail refuses is reported with "The email went to the others."
- **A write in the catalogue for both entries.** `writeTools` is `["gmail_send_reply", "gmail_send_message"]` on `google-workspace` and on `google-imap`; a recorded "read" cannot narrow it, as for the reply. Background runs (a check-in, research) are never offered it, because they are limited to reads.
- **Asked about every time.** Unlike a reply, "Always allow" is neither offered nor honoured for a new email: it is opened as a request with the policy `always_ask`, the approval store refuses `allow_always` for it, a saved rule for the same address does not answer it, and the app hides the button. A standing answer for one address must never send a later, different email. The card shows every recipient, the subject and the whole body (folded behind "Show all N characters" when long, never cut); the chat-channel card is bounded and says so ("Not all shown").
- **Who has it.** Only Otto, through the new skill `send-a-new-email` (`examples/freeduet/skills.yaml`); the grant of the tool is an administrator's, as for every connector tool, and is not seeded. Iris, Penny and every other member are not offered it. Otto's prompt says a reply goes through `gmail_send_reply` and a new email through `gmail_send_message`, that an address is used exactly as written (never invented, corrected or completed, and asked about when it looks wrong), and that after sending he says plainly that it was sent, to whom, its subject and the text. Iris hands the request to Otto instead of refusing.
- **When it needs no card at all**, see D27 below.

| # | Decision | Why |
|---|---|---|
| D25 | **A local Whisper, optional, off by default, switched on by one line in `.env`: `FREEDUET_DICTATION=local`.** (1) **A `whisper` service** in `docker-compose.yml`, behind the profile `whisper` so nothing starts or builds without the flag. How to run them is in `openbot/docs/configuration.md`, "Local Whisper" | An app for people who are not developers cannot start with "get an API key". A local model is the only way to promise that a recording never leaves the machine, and whisper.cpp is the smallest runtime that serves the OpenAI path, so the adapter, the route, the limits and the composer did not have to change. The model is pinned by hash because a download over the network is the one thing in this design that runs unreviewed bytes; the tag is pinned by commit for the same reason. The flag is off because a model of 574 MB and a container are not a thing to install by surprise, and a person who set up their own service keeps it. Limits:

- **CPU only in v0.1.** The image is built for the computer that builds it and uses no GPU. How long a request takes is what 7a reports on the maintainer's computer; it is not guessed here.
- **A recording is at most 120 seconds**, as for every provider, and one transcription per person at a time. A long dictation on a slow computer can pass the 60 seconds the route allows a provider and then fails with the existing "timed out" message.
- **A phone needs https.** On `http://<computer>:3010` the browser offers no microphone. The two ways out (use the computer itself, or put the app behind https) are in the configuration guide; neither is built.
- **The whisper port has no sign-in.** It is on loopback only, but anything running on that computer can reach it, and whisper-server answers any origin (`Access-Control-Allow-Origin: *`, `server.cpp:739`). What a caller can do: send it audio and read the transcript (that costs CPU time and exposes nothing the caller did not already hold), and `POST /load` (`server.cpp:1175-1210`) with the path of a file in the container, which makes the server drop its model and, when the file is not a model, `exit(1)`, so the service stays down until `start.sh` is run again. Nothing is read back from the container's files. A web page in the person's browser needs to get past the browser's own protection of local addresses to do any of this. It stays as it is until a request is made to put the service anywhere but loopback, and that should come with a token. Whisper.cpp v1.9.5 has no option to turn `/load` off.

### D25 amendment, 2026-11-11: measured on the maintainer's computer

First real run (32 threads, 61 GB, `large-v3-turbo-q5_0`, no language sent): word error rate **2.9%** on 100 FLEURS clips, no failed request, but **17.26 s** median and 20.85 s at the 95th percentile per request, and 7c failed ("Thank you." on digital silence, "." on room noise). The service log said `n_threads = 4 / 32`. What changed, from the source at v1.9.5:

- **Threads.** The server takes `min(4, hardware threads)` (`examples/server/server.cpp:73`, `--threads` at :210, applied at :936). The service now takes `WHISPER_THREADS`, by default half of `nproc` clamped to 4..16 (`openbot/whisper/threads.sh`, tested). Whether 16 is the best number for a given computer is for the maintainer to measure with the override.
- **Decoding.** The server is already **greedy** unless `beam_size > 1` (default -1, :82; strategy chosen at :927; `best_of` 2 at :81 only matters on the temperature fallback). So beam search was not the cause of the slowness and stays off; `WHISPER_BEAM_SIZE` (`--beam-size`, :218) lets the maintainer measure it without a rebuild. Temperature fallback (`temperature_inc` 0.2, :89) can only be switched off by a request field (:582): the server's `--no-fallback` is parsed (:228) and never used. It is not touched, because turning it off is a quality trade nobody has measured.
- **Silence, (a) options.** The server and library offer `--suppress-nst`, `--no-speech-thold` (:247) and `--logprob-thold` (:222), but a segment is dropped only when both the no-speech and the log-probability conditions hold (`src/whisper.cpp:7780`), and `logprob_thold` also drives the fallback re-decoding, so raising it is not a clean silence control. Not used.
- **Silence, (b) the response (tried, replaced).** `response_format=verbose_json` gives each segment `no_speech_prob` (`server.cpp:1154`). It was built and measured, and the service reports 0.000 on every segment, silence included, so a filter on it cannot work. Removed; see the second amendment.
- **7b** uses the ffmpeg in the built whisper image through `docker run` (no network, no capabilities, the caller's user, one folder mounted) when the host has none.

### D25 second amendment, 2026-11-11

Measured with 3348a56 (16 threads): 100 clips, language detected: `large-v3-turbo-q5_0` WER 2.8%, median 9.78 s, p95 17.42 s, 783 MB; `large-v3-turbo` 2.9%, 8.01 s, 8.79 s, 1.75 GB; `small` 7.9%, 1.83 s. Threads (q5_0, 30 clips): 8 gave 14.14 s, 16 about 9.8 s, 32 10.92 s, so the cap of 16 stays. At 4 threads, detection 17.26 s against 8.64 s with `it`, same 2.9%. 7b passed (wav, webm/opus and mp4/aac all 2.1%, through the image's ffmpeg). 7c failed again, with `no_speech_prob` 0.000 everywhere.

- **VAD on for the local service.** Hand-run by the maintainer on the same image, `--language it`: without VAD, 5 s and 30 s of silence gave "Grazie a tutti.", noise "Grazie."; with `--vad --vad-model ggml-silero-v5.1.2.bin` all four were empty, 2 s of speech kept, a full clip and a clip followed by 10 s of silence kept, WER on 30 clips 1.1% against 1.4% without, median 10.3 s against 8.7 s. The entrypoint passes `--vad --vad-model` (`server.cpp:260-261`, applied at :968-976) unless `WHISPER_VAD=off`. The VAD options stay at the server's defaults, none exposed: threshold 0.5 (:125), minimum speech 250 ms (:126), minimum silence 100 ms (:127), no maximum speech (:128), padding 30 ms (:129), overlap 0.1 (:130). The server's own default is VAD off (:123).
- **The VAD model is pinned like the Whisper ones**: `ggml-silero-v5.1.2.bin`, 885098 bytes, sha256 `29940d98d42b91fbd05ce489f3ecf7c72f0a42f027e4875919a28fb4c04ea2cf`, from https://huggingface.co/ggml-org/whisper-vad, read from the file's Git LFS pointer (`/raw/main/ggml-silero-v5.1.2.bin`) on 2026-11-11 and equal to what the maintainer's download gave. Fetched with the same checksum-verified code (`openbot/whisper/fetch-model.ts --vad`). Its licence is not recorded in NOTICE.md yet: the Silero VAD project is MIT, to be confirmed against the repository's model card.
- **A caution from Dictatum** (a dictation app made by the same group as FreeDuet; more about it later), as the coordinator relayed it: VAD together with a vocabulary prompt on dictation with long pauses can cut speech. Not reproduced here (the pause case below is the guard), which is why `WHISPER_VAD=off` exists and the prompt is optional.
- **The no-speech filter and the verbose request are gone.** The local adapter is back to the plain request; `joinSegments` stays because VAD output still has line breaks between segments.
- **7c guards the other way, with whole clips.** Besides the four silent cases: 2 s of speech then 10 s of silence still returns words of the sentence. The 2 s start at the speech onset (the first 20 ms window whose RMS is above 5% of the clip's own peak), 100 ms before it, and at least 1 s of them must be above that level, else the next cached clip is used: the first 2 s of a FLEURS clip are mostly lead-in silence, which VAD rightly drops. One more row, "a short word: 0.6 s from the onset, then 3 s of silence", is measured only: printed, never failing; one clip with a 3 s pause inserted in its middle is no more than 2 WER points worse than the clip alone; two whole clips with 5 s of silence between them and 3 s after return at least half of the words of each sentence. A clip cut mid-word proves nothing, so none is used.
- **Language is told, not detected.** Order: `TRANSCRIPTION_LANGUAGE`; else the browser's primary language subtag sent with the recording (the app has no language setting of its own: no i18n, no per-person preference), accepted only if it is exactly one of Whisper's two-letter codes, else dropped; else detection. Local service only: other providers ignore the hint, so their request is unchanged. Limit: a person whose browser is not in the language they dictate must set `TRANSCRIPTION_LANGUAGE`.
- Default model unchanged (`large-v3-turbo-q5_0`); the measured table is in `configuration.md` for the maintainer to choose from.

## 10. A new email goes out on the person's own written request (D27)

Added on 2026-11-12, by the maintainer's explicit decision while D24's fifth tool was being built: when he writes "write to <address>", it must do it. He has already approved by writing it, and a second card asking the same thing is noise. The decision covers `gmail_send_message` only. `gmail_send_reply` is exactly as it was, and nothing else about an account action changes.

| # | Decision | Why |
|---|---|---|
| D27 | **A new email is sent without a card when, and only when, every one of these holds, checked on the server at the approval gate and never from what the model says about itself; in every other case it waits for the person.** (1) **The run is the person's own live chat turn.** The run carries no initiator, which is what a turn started from the app carries. A routine, a check-in, a memory run, the deployment, a task, a message delivered from another channel, a group conversation, the continuation after another approval and every hand-off carry an explicit initiator and fail this condition (`typed-recipients.ts`, `recipientsTypedByPerson`, called from `plugin-store/calls.ts`). (3) **Every recipient is one whole word of that message**, equal ignoring case and surrounding spaces. The person's own "ask before making changes" setting and any team rule that asks still open a card as for any write | "The person's own written request is the approval." Delegation must never launder an account action, so a Bot writing an address into a brief, a memory or a stored prompt is not "typed by the person", and any doubt resolves to asking |

### Amendment (2026-11-12): the person asks Iris, and Iris hands the email to Otto (D27a)

D27a lets it go out with no card **when the server itself can show that the hop came from the person's own typed message, and only then.** Nothing the model writes can set, change or read what the server relies on.

| # | Decision | Why |
|---|---|---|
| D27a | **The mark.** When a member calls `message_bot` during the person's own live chat turn (the run's continuation carries no initiator, exactly D27 condition 1), the server records on the hop's own queue row, beside the envelope and never inside it, who the person is, which conversation and run the hop was made in, and the id and a SHA-256 of the person's latest typed message of that turn (`agents/handoff-request.ts`, `handedRequestOf`, called from `agents/handoff-tool.ts`). The audit row says `approvedBy: person_request`. The person's own "ask before making changes" setting and any team rule that asks still open a card | The person's own written request is the approval, and it does not stop being theirs because they wrote it to the head of the team. Any doubt resolves to asking |

**After a send with no card, the person is told.** Otto's prompt already says to tell them that it was sent, to whom, its subject and the text. Iris's "How you handle results" now says the same when a colleague reports an email sent, and that her three-sentence chat limit does not cut it short, so the answer the person reads from Iris says it plainly.

**What is not verified, and what would change it.**

- **Not run end to end on a live stack.** The conditions are proved by tests through the real gate, the real queue rows and the real thread store (`send-message-approval.integration.test.ts`, `handoff-request.integration.test.ts`, `handoff-request.test.ts`), with a fake mail backend. No eval was added: the eval stack has no Gmail. - **A built-in (in-process) Bot** gets no hand-off claim on its run assertion, so a hop to it asks. Only the remote members that FreeDuet runs through agent-freeduet are covered.
- **A shared channel's other members.** The conversation holds messages by several people in a channel; the origin message is whatever the conversation stores as the person's latest, the same limit the direct rule has.
- **"Once per message" is in the server's process** (like "once per run"): a restart forgets it.
- **The forward hop is a scratch thread.** When a hop does ask, its card is in the person's approval list and not in a conversation they are looking at; that is as before.

**What is not covered, and what would be needed.**

- **A hand-off asks unless the server itself recorded where it came from.** The rule above is the direct case. - **The window is one message.** An address typed two messages ago asks again. A wider window needs the same provenance mark on each message, because role `user` also holds the server's own messages (a routine's prompt, a task's, a delivered one) with nothing to tell them apart in an old history.
- **What the person's words cannot show.** A message the person sent by tapping a suggestion a Bot wrote is still theirs, and an address inside a short paste in their own message counts. The card exists for every other case.

Several different emails to the same typed address in one run are each sent (only an exact repeat is stopped); a per-run cap is a decision for the maintainer.
- **The "once per run" memory is in the server's process.** A restart forgets it, and a new run is a new request.
- Evals: the cases that say "any email goes through the send tool and its approval" (`iris-4`, `portia-3`) are about a member without the tool, or an address nobody typed, and still hold; no eval for a typed address was added, because the eval stack has no Gmail connected.

## 11. A secret per installation, so a container is not taken for the person (D28)

Added on 2026-11-14, the follow-up that #116 left open (the roadmap item "A secret per installation for the no-sign-in mode"). With no sign-in (`OPENBOT_SINGLE_USER`) the person is the administrator, and since #116 that is only a request whose TCP peer is this machine's loopback. That settles Linux and WSL, where a container reaches the server on the Docker bridge and its peer is the bridge. It does not settle Docker Desktop (Windows, macOS), where a container that calls the host's published port is carried through the VM's own proxy and arrives as 127.0.0.1, the same peer as the person's browser. A Bot's computer is such a container, and it runs what a member, or a page it opened, asks of it.

| # | Decision | Why |
|---|---|---|
| D28 | **In single-user mode, a request from this machine's loopback is the person only when it also holds this installation's secret.** (1) **One secret, made once, by the script that already keeps the install's other secrets.** `scripts/start.sh` writes `FREEDUET_INSTALL_SECRET` (32 random bytes as hex) to the settings file, mode 600, the first time it runs without one. An install from before this gets it on its first start after the update, and that start restarts the server, which reads its settings once. The script never prints it and never exports it: Compose and the Bots' containers are children of the script. (2) **The server asks for it wherever it asks for the peer rule, through one function** (`server/src/auth/install-secret.ts`, `personVerdict`): the guard behind every person-only route (`/api/approvals` among them), the CopilotKit mount (`/api/copilotkit/*`) and the live-screen upgrade. A loopback peer without it gets 401 with the code `pairing_required`; any other peer gets what #116 gave it. It is not asked of a deployment with sign-in, of one opened with `OPENBOT_HOST` (everybody who reaches it is the administrator, which that setting says and the boot log repeats), or of a server started by hand with no secret (the peer rule alone, and the boot log says so). A value that is set and cannot be a secret stops the boot, because ignoring it would switch the protection off quietly. (3) **The browser gets it as a cookie that only a one-time link sets, and the person types and pastes nothing.** `scripts/open.sh` calls `POST /internal/pairing` with the secret as a bearer token (loopback only) and is given `/api/pair?token=`: 256 bits, good once, for 120 seconds, at most 16 outstanding, kept in memory. It opens that link, and `GET /api/pair` answers 303 to `/` with `freeduet_install_<server port>`: HttpOnly, SameSite=Strict, host-only, `Path=/api`, 400 days, not Secure because the app is `http://localhost`. `start.sh` runs `open.sh` by itself on the start that made the secret (not in CI, not for the eval stack, not with `FREEDUET_NO_BROWSER=1`); a later start opens nothing, because that browser holds the cookie. Another browser, or this one after its cookies were cleared, runs `bash scripts/open.sh`, and the sign-in screen says so. The scripts that call the server as the person (the health check in `start.sh`, the clean-start check, the eval stack and runner, the dictation e2e) send the same cookie. (4) **No path from the secret to a Bot's computer.** It is in no environment and no mount of a computer (the supervisor builds that environment from an allow-list and mounts the Bot's own two volumes), in no Compose service (`environment:` or `env_file:`), in no response except the one that pairs a browser (which needs a link only `open.sh` can get), in no URL (a link is spent when it is used), in no log (a pairing is logged as minted, paired or refused, and nothing else), and on no command line (`curl -K` with a file of mode 600, removed at once). Service-to-service calls keep their own credentials (`AGENT_TOOL_TOKEN`, `WORKER_SHARED_SECRET`, `COMPUTER_TOKEN`, `FREEDUET_LOCAL_KEY`) and are not asked for it. A deployment with sign-in is exactly as it was | With no sign-in a network position is all that makes a request the person's, and on Docker Desktop that position is the same for the browser and for a container. A secret turns the position into a proof, and the person has to do nothing for it: the scripts they already run make it and hand it to the browser. It is a cookie because the browser must send it on every call and on the live screen's WebSocket without a page script ever holding it; the link is single-use because a long-lived secret in a URL ends up in history and logs. The design is the smallest one that closes the case: one module, one function the three places ask, and no new store |

**What is verified, and how.**

- **By tests, against a real Postgres, a real `startHttpServer` and a real `createApp`** (`server/tests/install-secret.test.ts`, 47 tests): a loopback request without the secret is refused on `/api/approvals`, on `/api/copilotkit/*` in every spelling of its path, on the channel socket and on the live-screen upgrade, and with the secret it is admitted; no header (`X-Forwarded-For`, `Host`, `Origin`) makes a request the person; the link is good once and for 120 seconds; no GET route of the assembled app answers a container with the secret, and the two pairing doors answer it nothing; a deployment with sign-in, one opened with `OPENBOT_HOST` and an install with no secret yet behave as before. No Compose service, `env_file` or mount reaches the secret, and the supervisor's allow-list does not carry it (`tests/compose.test.ts`, `supervisor/tests/install-secret.test.ts`). The scripts are exercised through fakes in `scripts/start-restart-guard.test.ts`: a first start makes one secret, mode 600, restarts the server, prints and exports nothing, and keeps the file's other settings; a later start keeps it; the cookie reaches curl through a file and never an argument; the browser is opened once, on the link and nothing else.
- **In a real browser** (Chrome 153 against a real server, the real app on its dev proxy and a real database; run by hand, not a committed test): an unpaired browser is told to pair, and its calls and its live-screen WebSocket handshake are refused; after the link it works through the proxy, and Chrome sends the cookie on the WebSocket to the server's own port from a page on another port of `localhost`; the cookie has the attributes above; the same link a second time pairs nothing; a page on another site does not send it; `127.0.0.1` is another cookie jar and asks to pair.
- **Not reproduced: Docker Desktop itself.** There was none to run on. That a container's call arrives there as loopback is the premise of #116's follow-up, not something this PR measured; the tests stand in for it with a request whose peer is loopback and that holds no secret, which is the same request to the server. **To check on Windows or macOS with Docker Desktop,** start the stack, let `start.sh` open the app, then from inside a Bot's computer container call `http://host.docker.internal:3001/api/approvals` with any HTTP client: it must answer 401 with `pairing_required`, while the paired browser works.

**Limits.**

- **The secret separates the person from containers and the network, not from the person's other programs.** A program running as the same user on the host can read `.env` or the browser's cookies, and could before.
- **A cookie belongs to a browser's cookie jar and to a host name.** A second browser, a private window, cleared cookies, or `127.0.0.1` for `localhost` asks to be paired again: `bash scripts/open.sh`. Tabs of the paired browser share the cookie.
- **For its two minutes the link is on the opener's command line**, which other programs of the same user can read. It is good once.
- **The links are in the server's memory.** A restart between `open.sh` and the browser loses the link; run `open.sh` again.
- **Rotating:** delete the line and run `scripts/start.sh`. It makes a new one, restarts the server and opens a paired browser; every other browser pairs again.
- **A cookie is shared by every port of a host,** so its name carries the server's port, and two installations on one machine (the real stack and the eval stack) keep one each. Another page on `localhost` is stopped from using it by the same-origin guard (`auth/same-origin.ts`), which asks the `Origin` of every write and every WebSocket.
- **The first start after the update opens a browser window by itself,** and says so. With `FREEDUET_NO_BROWSER=1` it prints the command instead.

## 15. With no sign-in, only this machine's own names are answered (D32)

## 16. A tool nobody calls a read is a write (D33)

**Decision.** For every catalogue entry, an advertised tool counts as a read only when the entry's `readTools` names it. Anything else the entry advertises is a write and asks the person (`classifyTool`, `openbot/server/src/plugins/catalogue.ts`). `readTools` is now required on every entry. For a tool a hub hosts (no catalogue entry), the provider's own "read" label is no longer enough when the tool's name carries a word of the credentials, security-settings or payments floor; such a tool is a write and the floor hands it to the person.

**Why.** Before this, an entry with no read list treated an advertised tool that the write list had missed as a read, so it ran with no card. Notion had 14 names on its write list against a server that advertises dozens, so `notion-delete-pages` and `notion-delete-databases` ran unasked. Drive and routines had the same shape. A hub tool's label is the provider's word, and a "read" on a name like `..._LIST_PASSWORD_POLICIES` was taken at face value.

**What changed.**

- Read lists derived from evidence only. Drive: its four adapter tools (`google-drive-rest.ts`). Notion: `notion-search` and `notion-fetch`, the two reads the recorded fixtures use. Routines: `list_routines` and `list_triggers`.
- Drive's entry no longer names `create_file` and `copy_file`. The scope is `drive.readonly` and the REST adapter only issues GET requests, so the connector never had a write; the old list described tools it does not offer. A tool added later by widening the scope asks until somebody reads it and lists it.
- Gmail (both connections), Calendar, and the search connectors classify exactly as before; `tests/fixtures/classification-before.json` is the table generated from main before the change and pins it.

**Limits, for the maintainer.**

- Notion's other reads (`notion-get-comments`, `notion-get-users`, `notion-query-data-sources`, the `notion-list-*` family and more) now ask. Notion's documentation describes them but labels none of them, so they are not listed until the first Refresh tools shows the live names and a person adds them to `readTools`.

## 18. A routine or a trigger never acts on an account without a card, and Full access does not unlock setting one up (D35)

Added on 2026-11-14, by the maintainer's decision (D35).

**Decision.** (1) A write made inside a server-run routine or trigger run always goes to the approval gate and waits for the card. Full access in either setting, the person's own rules and preferences, a saved "Always allow", an administrator's team rule that allows, the reviewer saying "proceed" and the D27 and D27a no-card email shortcut never answer it; the card can be allowed once or refused. (2) Creating, changing, switching on or off, or deleting a routine or a trigger always asks with a card, in the person's own live chat too, with Full access on or off. (3) Reads, the person's own live turns (apart from (2)) and hand-offs along the hub grants (D21) are as they were. The server decides, from what it holds; nothing the model writes can add the card or lift it.

**Why.** Nobody watches a routine. In the person's own turn the person is there, and Full access, "ask before making changes" and auto-review are their own settings for that. A routine runs at nine in the morning over mail and pages nobody sees, and what stood between it and an account was a model reading text the routine itself wrote (the reviewer) and a rule the person saved once for a chat. Both holes were verified on main (7e5800c) before anything was changed:

- **(a) A routine's write could pass with no card.** `decideAction` (`server/src/approvals/policy.ts:468-616`) never read who started the run. `evaluate` (`approvals/service.ts:320-370`) used the initiator for Full access and for the audit trail, and for nothing else. So a write by a routine or an event trigger was allowed when the reviewer said "proceed", which is the default (`policy.ts:610-615`); when the person had saved an allow or pre-approved rule (`policy.ts:578-601`); and when "ask before making changes" was off (`policy.ts:603-609`). Full access itself did not apply to a routine (`freeduet/full-access.ts:139-150`), so that was not the hole.
- **(b) Full access unlocked setting up a routine, and so did the person's defaults.** The Routines connector's seven writes (`plugins/catalogue.ts:561-587`, transport `builtin-routines`) are plain writes. With Full access on, in either setting, `fullAccessOutcome` (`policy.ts:293-315`) allowed them in the person's own turn with no card (`service.ts:335-336` asks Full access for every action that is not a read); only the safety floor, which reads words, or an administrator's team rule that asks could stand in the way, and a routine whose instruction names no payment, credential or security word went through. With the person's defaults (auto-review on, "ask before making changes" off) a member without Full access did the same, because the reviewer said "proceed". A Bot could set up an unattended run by itself.

**The rule as built.**

- `server/src/freeduet/always-ask.ts` (new, FreeDuet's own, pure): `alwaysAskReason(facts)` says why the server holds an action to a card, or says nothing and the gate goes on as before. Only for `effect: "write"`. Never for the Bot's own files and commands on its computer or the person's (`NOT_ACCOUNT_ACTIONS`: they reach no account). The run is **unattended** when its initiator is a `routine`, a `responsibility`, or a hand-off whose `origin` is one (the kinds are listed under the limits below); the initiator is the approval context's (set from the signed run) or, for a call that holds no approval context, the call's own. The call is **setting up** when the plugin store marked it a write on the Routines connector.
- `approvals/policy.ts`: `decideAction` takes an optional `alwaysAsk`. Given one it does not look at Full access, and no rule, preference or reviewer "needs approval" changes the answer: the outcome is `ask` with `source: "always_ask"`, the source a new email already has (D27), for which the store refuses "Always allow", no saved rule answers it, and both cards hide the button. It sits **after** every hand-off, because a hand-off is stricter than a card and still wins: the safety floor, a rule that hands the action to the person, and the reviewer's own safety or hand-off verdict. `NOT_ACCOUNT_ACTIONS` is exported. +22 −3.
- `approvals/service.ts`: `evaluate` computes `alwaysAsk` from facts the server holds, does not ask Full access about an action it holds, and writes the initiator on the trail for a call that carries its own. +18 −5.
- `approvals/types.ts`: `ApprovalCandidate` gains three optional facts, none of them in the digest: `initiator`, `configuresAutomation`, `answeredByCard`. +17.
- `plugins/plugin-store/calls.ts`: sets them. `initiator` is the signed run's; `configuresAutomation` is read off the transport the connection resolved to and the effect, never off a name or an argument; `answeredByCard` is set when the send check has just put this exact new email on its own card and the person allowed it. +15.
- The app is unchanged: it already hides "Always allow" for `always_ask`. The card's reason says, in two sentences, that it came from a routine or a trigger running on its own, or that setting one up, changing it or deleting it always asks.

**A routine's new email is asked once.** D27 never applied to a routine (`typed-recipients.ts` needs a run with no initiator) and still does not: the private-share check already puts a routine's new email on a card every time, and the person's answer is spent on the first allowed retry. A second card from the gate for the same email could never be honoured, so `answeredByCard` makes the share card the card. Any other write of a routine gets its own.

**What is not changed.** Reads. The person's own live turns, with Full access on or off, apart from the seven setup tools. Hand-offs along the hub grants (D21: the hand-off itself, `effect: "delegate"`, stays pre-approved); what the receiving member then writes in a hop that began in a routine or a trigger meets this rule in its own run, and a hop that began with the person meets what it met. Memory runs and the deployment. The Bot's own files and commands (`NOT_ACCOUNT_ACTIONS`). D27 and D27a, for the person's own typed recipients. The safety floor and every rule that hands an action to the person, which come first.

**What is verified, and how.** On a real Postgres, through the real gate and the real plugin store (the Routines connector over recording stores, the app-password mailbox over a fake one), Full access on in both settings:

Pressing Download fetches `GET /api/computers/:botId/files/download?path=...` as the signed-in person, reads the answer as a blob whose type is forced to opaque bytes, and hands it to the browser as a file to save under a name made safe to save. The card has no link to follow and no frame to open the file in, so a page a member made never runs in the app's origin. (4) **The tool is not offered** where the deployment has no computer, where the person may not use that member's computer (`canUseComputer`), where the person switched the computer off (`cloudComputer`, the rule of `computer/offered.ts`), or in a background run that can only read (`proactive/restriction.ts`). | Reusing the route means the offer and the button are judged by the same things: the deployment's own `download_file` rule, the audit trail, and the computer's confinement and size limit. A check of our own at offer time would be a second check that could disagree with the first, and a card that carried a link would be a link that works for somebody else. |

**The rules, exactly.**

- **The path.** The tool takes one `path`: trimmed, 1 to 1024 characters, no control character, and no other argument (the object is strict). It has no way to name another member: the member is the one the tool was built for, and the card names that member. Everything else is decided by the gateway and by the computer (`agent-computer/src/workspace.ts`, `resolvePath` :110-194): an absolute path is refused, even one that points inside `/workspace`; so is any `..` segment, written with `/` or with `\`; the real path of the file must stay inside the workspace, so a link to a file or a folder outside it, or into another member's workspace, is refused; a folder is a 400, a missing file a 404. A percent-encoded path is only a name: the route decodes it once, so `..%2f` typed into a URL becomes `../` and is refused, and a double-encoded one is a file name that is not found.
- **The size.** `DEFAULT_WORKSPACE_LIMITS.downloadBytes`, 100 MiB (`workspace.ts:97`), enforced by the computer before any byte is sent, the same for the offer and for the button, and not configurable today. A file one byte over is a 413 and the member is told to make it smaller.
- **Who may press it.** The existing route, unchanged: `requireUser`, then the Bot check of `server/src/computer/routes.ts:77-102` (`canUseComputer`: an administrator, a public Bot, or the Bot's owner), then `routes.ts:660-679`. Nobody signed in gets a 401, a session with no role a 403, another person's private Bot a 404 ("There is no such Bot.") and the computer is not asked, and a Bot's computer calling with its own token and no session gets a 401. The tool is built for the person whose run it is, so the card is drawn in that person's own conversation.
- **What the answer is.** `Content-Type: application/octet-stream`, `Content-Disposition: attachment` with a filename made safe, `X-Content-Type-Options: nosniff` and `Cache-Control: private, no-store` (`shared/file-download.ts:51-65`, used as it is). ## 23. The computer and the supervisor answer, from this machine's loopback, only to this machine's own names (D40)

Added on 2026-11-14, as the follow-up to D32. D32 stopped a page whose name was re-pointed at 127.0.0.1 from reading the API server. Two more services answer HTTP on the same machine and had the same defect: the Bot computer (`agent-computer`) and the container supervisor, which holds the Docker socket. This is D32's rule in each of them.

| # | Decision | Why |
|---|---|---|
| D40 | **In `agent-computer` and in `supervisor`, a request whose TCP peer is loopback is refused with 421 unless its `Host` names this machine or a configured host.** (1) **Allowed:** `localhost`, any address of 127.0.0.0/8 or `::1` (including IPv4-mapped), `host.docker.internal`, and the names listed in a new setting of that service, `COMPUTER_ALLOWED_HOSTS` or `SUPERVISOR_ALLOWED_HOSTS` (comma separated, each `host` or `host:port`, an IPv6 address in brackets). A value that is set and is not such a list stops the boot and names the entry, because a name dropped in silence would show as a 421 with no reason. Unset means no extra names. (2) **Read exactly as D32 reads it:** hostname only, not the port; case-folded; one trailing dot dropped; addresses in the URL parser's canonical spelling (so `2130706433` is `127.0.0.1` and `3232235777` is not loopback); userinfo, paths, lists, repeated headers, a port above 65535 and a missing header are refused. (3) **First thing in each service's request path,** before `new URL(request.url)`, the token check, any route, the live-screen upgrade or a call to Docker. `/health` is held to it too. (4) **Not applied** to a peer that is not loopback or cannot be read: another container, a kubelet, the server calling `supervisor:4300`. (5) **A copy, not an import.** Each image holds its own package's `src` and nothing else (the computer also `shared/file-download.ts`), and each package has its own lockfile, so neither can import the server's `auth/host-guard.ts`. Each carries a copy of the header reading (`agent-computer/src/host-guard.ts`, `supervisor/src/host-guard.ts`), and `openbot/tests/host-guard-copies.test.ts` fails when a copy stops answering as the server's does. | A name a page controls must not reach a shell, or the four verbs that remove a Bot's computer, with a token that is public by default. The `Host` is the one thing the page cannot choose. A copy that a test holds to the original is the smallest change that does not make two small images carry the server |

**What the rule does not reach: a published Docker port.** In bridge networking the daemon's proxy opens the connection to the container, so the process inside sees the network's gateway as the peer and not 127.0.0.1 (read in third-party documentation of Docker's userland proxy, whose connection listing shows the container's peer as the bridge gateway, `172.17.0.1`; **not measured here, there is no Docker daemon in this sandbox**). So on the stock layout, where the server and the computers reach each other through published ports, this rule is inert, and the token alone is the gate there. Where it bites is wherever the peer really is loopback: a computer or supervisor run directly on the machine (development; `scripts/start-local-chrome-computer.ts`, which drives the person's installed Chrome on `127.0.0.1:4101`), and the all-in-one image's own processes. What a given engine does with a published port (Docker Desktop, Podman, Colima) was not measured.

A rule keyed on "the peer is the gateway of my network" was not built: a kubelet's probe arrives from the node with the pod's own address as `Host` and would be refused; source NAT can hide the gateway; and it cannot be tried without Docker. That is a security decision, below.

**Not done: refusing the public default token inside the service.** `start.sh:109-110` and `docker-compose.yml:108,206-208` hand the public default to every install that sets none, and `start.sh` writes it into `.env`. `.env.example:380` leaves `COMPUTER_TOKEN=` empty, and the clean-start job (`freeduet-clean-start-check.sh`, which sets no computer token) starts the computer with the default and waits for `/health` at `start.sh:526`. A refusal in the service would stop that job and every existing install, whose computers start with the default. The eval stack already uses random tokens (`freeduet-eval-stack.sh:109-110`). Another change makes the token random per installation in `start.sh` and Compose; this change does not touch either file. When it lands, refusing the known default in each service is one line and a test, and it is what closes the stock path above.

## 22. No secret starts on a value this repository publishes: `start.sh` makes each installation's own (D39)

Added on 2026-11-14, the follow-up of a security review of the one-command start (`scripts/start.sh`, `docker-compose.yml`, `.env.example`). D28 (section 11) gave each installation one secret of its own. Five others still started on a value written in this repository, the same on every installation, and nobody ever changed them because `start.sh` supplied them and `.env.example` said so. A secret that is the same everywhere is not a secret: whoever has read the repository holds the key to every installation that kept the example.

| # | Decision | Why |
|---|---|---|
| D39 | **None of the secrets the one-command start uses falls back to a published value; each installation makes its own.** (1) **Made once, by the script that already makes the others.** `scripts/start.sh` makes, with `openssl rand`, `SUPERVISOR_TOKEN`, `COMPUTER_TOKEN` and `WORKER_SHARED_SECRET` (32 bytes, hex), `KEY_ENCRYPTION_KEY` (32 bytes, base64) and the database's password (24 bytes, hex: `POSTGRES_PASSWORD` and the `DATABASE_URL` that carries it). Each is written to the settings file the first time a run finds none, the way `FREEDUET_INSTALL_SECRET` is (mode 600, the file rewritten through a temporary file), and read, not made again, by every later start. The run prints a line saying what it made and where (`Generated NAME and wrote it to .env.`), never the value; no value is on a command line, in a log, or in the environment of curl or of a container that has no use for it. (2) **A value somebody set is theirs.** One in the environment is used as it is and written nowhere. One in the file is kept, unless it is, character for character, a value this repository used to publish (`scripts/secrets.sh`, the one file they are still written in) or, for the database, the example address `postgres://openbot:openbot@localhost/openbot` in any of its spellings: that is what an older `start.sh` wrote to `.env`, or `cp .env.example .env` copied, and it is nobody's choice. A `DATABASE_URL` with another password, user, host or database is never touched. (3) **The files publish none of them.** `.env.example` ships `DATABASE_URL` and `KEY_ENCRYPTION_KEY` empty and says that `start.sh` makes the rest; `docker-compose.yml` no longer defaults `COMPUTER_TOKEN` or `SUPERVISOR_TOKEN` (`agent-computer` and the supervisor both refuse to start on an empty one, which is the right way for a Compose started by hand with no `.env` to end), and `postgres` and `migrate` read one setting, `POSTGRES_PASSWORD`. The one fallback that stays is `${POSTGRES_PASSWORD:-openbot}`: a database made from nothing needs some password, and the desktop app starts this file with a database address of its own and no password. The eval stack no longer writes the public database address or four secrets of its own: `start.sh` makes them in `.env.eval`, with that stack's database port. (4) **An installation already on the old values is moved off them without losing anything** (next section). (5) **What cannot be changed safely is left, and said on every start.** | A published value is a credential everybody has. The supervisor's token cycles any Bot's computer, the computer's token drives a browser that holds the person's logins and runs commands (one token for every computer, so one Bot's computer could drive another's), the worker's secret dispatches a routine run, and the database's password and the vault key together open everything the installation stores. Each is reachable from the person's own programs and, on Docker Desktop, from a Bot's computer, whose calls arrive as loopback (D28's premise). The fix costs the person nothing: the script that supplied the public value supplies a private one. It is the D28 pattern, extended. Two of the five are not "write a line": the database keeps the password it was created with, so it is set on the running database first and written down only once the database holds it; and what the key sealed is unreadable under another key, so it is replaced only where nothing is sealed |

**What was found, secret by secret.** Everything the single-user start path reads was walked: `scripts/start.sh`, `stop.sh`, `open.sh` and the files they source, `docker-compose.yml`, `scripts/freeduet-eval-compose.yml`, `.env.example`, `scripts/freeduet-eval-stack.sh` and the clean-start check, `examples/freeduet/`, `server/src/config.ts`, and the environment of `agent-freeduet`, `agent-computer`, the supervisor and the worker. File and line are as on main at 88b01af, before this change.

Not on the list because they have no published value. `AGENT_TOOL_TOKEN`, `MANAGED_AGENT_TOKEN`, `FREEDUET_LOCAL_KEY` and `FREEDUET_INSTALL_SECRET` are made per installation by `start.sh` already. `BETTER_AUTH_SECRET` is for a deployment with sign-in. `server/src/config.ts`, `agent-freeduet`, `agent-computer`, the supervisor, the worker, the toolkit and `examples/freeduet/` hold no secret with a literal default (`agent-computer/src/index.ts:120` and `supervisor/src/index.ts:61` refuse to start on an empty one). `stop.sh`, `open.sh`, `freeduet-eval-compose.yml` and the clean-start check read none of the five. One published value remains and is not on this path: `SPIRE_JOIN_TOKEN`, `openbot-dev-token` (`docker-compose.yml:167` and `:231`), for the SPIRE services that `start.sh` does not start.

**An installation that already runs on the old values, step by step.** What `git pull` and the next `bash scripts/start.sh` do, in order, and what the person reads:

1. **Three tokens.** A line that is empty, absent or still one of the old strings gets a new random value, written to `.env` (the line moves to the end of the file; comments stay). The run says `Replaced NAME, which was the example value published in this repository, with one generated for this installation, and wrote it to .env.` (`Generated NAME and wrote it to .env.` when there was none). A line the person changed is not touched.
2. **Compose.** It is declarative: the services whose environment changed (`agent-computer`, the supervisor) are recreated, in seconds. Their data are in volumes and are kept.
3. **The database.** Once Compose has it up, `start.sh` sets the new password on the running database, through the container's own socket (`ALTER ROLE openbot WITH PASSWORD ...`, the statement on standard input, so on no command line; it works whatever the old password was, and touches no data). It tries for up to 30 seconds. When the database holds the new password, `start.sh` writes `POSTGRES_PASSWORD` and `DATABASE_URL` to `.env` (same host, port and database, new password) and recreates the database's container, not its volume, so that Compose's own copy of the password matches. The run says `database: its password was the example one this repository publishes. It is now one generated for this installation, written to .env. Your data is untouched.` **If the password cannot be set** (the database does not answer, Docker refuses), `.env` is left exactly as it was, the start goes on with the old password, and says in red that it is still the example one and why, on every start until it works. With no `DATABASE_URL` at all and no way to set one it stops rather than start without.
4. **The migration** runs with the new password.
5. **The key.** `start.sh` asks the database how many rows hold something the key sealed (`credentials`, `saved_logins`, `sso_providers`; revoked rows count: the old key may be the only way to read one). **None:** the key is replaced, and the run says so. **Any, or the question could not be answered:** the key is left, and the run says in red on every start that it is still the example key, why it was kept, and that whoever gets a copy of the database can read what it holds. Nothing is ever re-sealed, so nothing the person saved is lost either way.
6. **The server and the worker restart once.** The server reads its settings at start, so a run that made or replaced a secret restarts it (the existing `SECRETS_ROTATED` path). The worker was only ever started when it was not running, so it kept the old secret and the old database password for as long as it lived, and every routine would have stopped firing without a word: it is now stopped and started again when either changed (`worker: its secret or the database's password changed, so it is restarted`).
7. **The Bots' computers.** A computer the supervisor made holds the old token. The supervisor replaces it the next time that Bot's computer is used, with its files, logins and browser profile kept (`supervisor/src/docker.ts`, `holdsCurrentToken`); what was running in it (an open page, a command) is lost.
8. **One line sums it up:** `Secrets that were the same on every installation have been replaced. The server and the worker restart once to use them, and so do the Docker services and Bot computers that held them. Nothing you saved is lost.` An installation that set every value itself reads nothing new and restarts nothing.

For a few seconds on the way (between the server's old connections and its restart), a request can fail where the server asks the database with a password it no longer holds; the start that caused it ends it.

**What changing a key that is in use takes.** `start.sh` leaves the key when the database holds anything sealed with it, and says so; this is what it points to. Nothing in the repository opens a row with the old key and seals it with a new one, so there is no supported way yet. The choices today are to leave the key, which makes the vault as private as the database is (a copy of the database is a copy of the vault), or to start the database again from nothing and connect everything again. What would make it a choice is a tool that re-seals every row in one transaction, with the server stopped and a backup taken first (decisions, below). The key is not rotated by deleting its line: with a vault in use that makes a new key and leaves every sealed row unreadable, the same as losing it. A new installation, and any whose vault is empty, gets its own key and has nothing to decide.

**Limits and decisions left to the maintainer.**

- **A vault in use keeps the public key.** An installation that has connected Gmail, saved a login or set up company sign-in is the one most worth protecting and the one this change cannot protect: its key stays, with a warning every start. A re-sealing tool would finish the job (a one-time script: stop the server, take a backup, open each row of the three tables with the old key and seal it with a new one in one transaction, write the key). It is the follow-up this section recommends, and it is a decision because it touches every stored credential.
- **An absent key is made, not asked about.** A `.env` that has lost its `KEY_ENCRYPTION_KEY` line (and has none in the environment) gets a new key even when the database holds sealed rows, which then stay unreadable until the old key is put back; the run says `Generated KEY_ENCRYPTION_KEY`. The server used to refuse to start in that state. Asking the database in this case too, and stopping when it holds rows, is a few lines and a test; it is not done here because a fresh clone, the case that matters, always answers none, and because the key being lost already is what made the rows unreadable.
- **The desktop app is not changed.** It already makes five of the six (`desktop/src-tauri/src/env.rs`, `MINTED` and `PUBLISHED`), but writes `postgres://openbot:openbot@127.0.0.1:<port>/openbot` itself (`env.rs:574-577`), so the Compose fallback `${POSTGRES_PASSWORD:-openbot}` stays for it, and the database's port is loopback only. Having the shell mint a password too is a small change in another surface with its own tests; its header comment, which says `start.sh` falls back to fixed strings, is now out of date.
- **`SPIRE_JOIN_TOKEN` keeps its example value.** `start.sh` does not start SPIRE; a deployment that turns it on should set its own.
- **For a few seconds a new database has the example password.** On a first start Compose creates the database with the fallback, and `start.sh` changes it at once; nothing is stored in it yet. Writing `POSTGRES_PASSWORD` before Compose starts would avoid even that, but only for a start that knows no volume exists, and asking Docker for that is more than this change needs.
- **A key replaced invalidates what was signed with the old one** that was still in flight: a run's assertion, a hand-off, a pending OAuth connection. They are minutes old at most. The Web Bot Auth identity, derived from the key unless `WEB_BOT_AUTH_KEY` is set, changes with it.
- **A Compose started by hand before any `start.sh` has no tokens,** and the computer and the supervisor refuse to start, saying why. That is the intended end; a person who wants one sets it in `.env`.
- **The Helm chart and the all-in-one image are not changed.** They hold none of the five values (the chart refuses the example key), and have their own secret handling.
- **`docs/ROADMAP.md` is not edited here.** The session that merges this updates it.
